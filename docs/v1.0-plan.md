# v1.0 — Detailed execution plan

The desktop release. This expands the roadmap's v1.0 spine (`roadmap.md` Phases
A–D) into a sequenced, file-level plan. The roadmap stays the strategic view;
this is the build order, the risks, and the exit criteria.

**Status (reconciled 2026-07-01): v1.0 is essentially COMPLETE.** All four
workstreams have landed — WS1 desktop shell, WS2 Polars engine, WS3 the full verb
set + Cube bridge, and WS4 the GPU renderer (via the HTML-in-Canvas pivot, not the
originally-planned WebGPU/Pixi path — see WS4). What remains is release packaging
(a versioned installer/portable artifact + a tagged GitHub release), not features.
Per-line statuses below are current.

## The three pillars → four workstreams

The author frames v1.0 as **Rust backend + wgpu renderer + relational
databases / extended Cube**. That maps to the four roadmap workstreams:

| Pillar (author's words) | Workstream | Roadmap phase |
|---|---|---|
| (foundation) | **WS1 — Tauri desktop spine** | A |
| Rust backend | **WS2 — Polars relational engine** | B |
| relational databases / extend Cube | **WS3 — the verbs + Cube bridge** | C |
| wgpu renderer | **WS4 — GPU renderer** | D |

The spine (WS1) underpins WS2 and WS4. WS2 → WS3 (verbs need the engine). WS4 is
**independent** of WS2/WS3 — it only needs the shell — so it can run in parallel
or slot in whenever zoom-at-scale becomes the live blocker.

```
WS1 Tauri spine ─┬─► WS2 Polars engine ─► WS3 relational verbs + Cube
                 └─► WS4 GPU renderer (independent; parallel)
```

**Build order rule (from the roadmap):** the legibility surface — inspector +
per-node frame previews — is built in WS1 *before* the WS2 engine swap, so Polars
drops in behind a UI that already reads frames. Most of that surface is already
done (`CableInspector.tsx`, `FrameDisplay.tsx`, `FrameChip`).

## WS2 — Polars relational engine (Phase B) — the keystone, highest risk

The real cost is an **engine-model change, not a dependency add.** Today a frame
cable carries a fully-materialized `FrameValue` (`frame.ts`). The target: data
**lives in the engine**; a frame cable carries a **lazy handle** (an opaque id
for a Polars `LazyFrame` query plan), and only at *display* does a node collect a
**preview** (schema + head-N + row count) across IPC.

### The central design decision: a `FrameBackend` interface (two implementations)

Do **not** scatter `isDesktop()` branches through ~30 frame nodes. Introduce one
seam:

```
interface FrameBackend {
  source(spec): Promise<Handle>            // literal / CSV / web → handle
  apply(h: Handle, verb, params): Promise<Handle>   // compose plan (cheap)
  preview(h: Handle, n): Promise<Preview>  // schema + head-N + rowcount (collect)
  column(h: Handle, name): Promise<TypedColumn>      // materialize one column
  drop(h: Handle): void                    // free the plan/handle
}
```

- **`JsFrameBackend`** (web demo + dev): a "handle" is the in-memory `FrameValue`
  we already have; `apply` runs today's eager `frame.ts`/`nodes/frame.ts` logic;
  `preview`/`column` are near-identity. **The web build keeps working unchanged**
  (Polars has no production WASM path — `compute-architecture.md`).
- **`PolarsBackend`** (desktop): `apply` composes a `LazyFrame` plan via `invoke`
  (cheap — no materialization); `preview`/`column` call `.collect()` head-N in
  Rust. Handles are ids into a Rust-side `HashMap<HandleId, LazyFrame>`.

The backend is chosen once at startup (`isDesktop() && gpuProbe-style capability`
→ Polars, else JS). Every frame node speaks the interface; the swap is one module.

### The sync → async wrinkle (call this out early)

`DataflowEngine` is push-based; `node.data()` may return a Promise (rete awaits
it), so **frame `data()` methods become async**. The scalar/list/number/formula
layer **stays eager JS** — only the frame layer goes handle-passing/async. The
boundary is exactly where a handle ↔ a materialized value:
- **Get Column / Get Row** materialize (handle → typed list/row) — the bridge
  back to the eager world.
- **Build Frame / a list-into-frame widen** (`coerceInputs.ts`) materialize the
  other way (eager value → handle).

**Risk:** mixed sync/async nodes in one engine pass. De-risk with a spike (below)
before committing the node migration.

### "Don't chat across the border" — why per-node IPC is fine here

`compute-architecture.md` warns against chatty borders. That warning is about
**per-element / per-iteration** messaging (the solver/sweep case), NOT per-node
plan composition. Lazy `apply` calls carry no data and don't materialize, so one
small message per frame node is cheap; we materialize **once** per visible
preview. Keep it that way: never collect except for a preview or an explicit
`column`/`row` bridge.

**Tasks**
- [x] Engine decided: **Polars** (2026-06-22), native Rust, lazy handles.
- [x] **IPC surface** (`src-tauri/src/ipc.rs` + `ipcBridge.ts`) — `engine_ping` +
  SolError-shaped `IpcError`, the contract the Polars commands land on. 2026-06-25.
- [x] **`FrameBackend` interface + `JsFrameBackend`** — done 2026-06-25
  (`frameBackend.ts`): the seam (`source`/`apply`/`join`/`append`/`preview`/
  `column`/`drop`) over opaque handles, JS backend keyed into a Map mirroring the
  Polars id→LazyFrame model. Nothing migrated onto it yet (live app unchanged).
- [x] Rust `PolarsBackend`: handle table, `source/apply/join/append/preview/column/
  drop` commands in `src-tauri`; `polars` crate (lazy feature set). **Parity-tested
  against `frameVerbs` (the JS oracle).** Done 2026-06-26 — `src-tauri/src/engine.rs`
  (+ `engine/tests.rs`, 27 cargo tests). A handle is an id into a Rust-side
  `HashMap<String, SolFrame>` (`DataFrame` + per-column `SolType` tags); the seam is
  `PolarsBackend` in `frameBackend.ts`, selected at startup by `initFrameBackend()`
  (desktop + `engine_ping` reports `"polars"`). Polars does select/drop/rename/
  filter/sort/join; the order-sensitive reshapers (group-by/pivot/unpivot/distinct/
  append) are computed in-engine over extracted columns for exact first-seen parity.
  Documented divergences (acceptable for v1): an input per-cell `SolError` → `null`
  on the way into Polars; string inequality is lexicographic (vs `localeCompare`);

  the seam — until then nothing consumes it, so the live app is unchanged.

  pure verb directly — so on desktop the verb **runs in Polars**, on web the JS
  backend (identical). **Pivot stays EAGER (working-specific):** `working`'s
  `PivotNode` is the full PIVOTBY (multi-field rows/cols/values, per-value funcs,
  totals, sort, relativeTo) whose `PivotSpec` exceeds the engine's simple pivot op
  — routing it would regress desktop to a basic cross-tab. Frame Lookup / Split
  Column / Add Index / Decision Matrix (working-only nodes) stay eager too. The
  DataflowEngine already awaits `data()`, so this was transparent to the engine.
  This first migration was transitional (collect-full per verb). **The lazy-handle
  finish landed 2026-06-30** (see dev-notes "Lazy handles on cables"): cables now
  carry a lazy `FrameRef` and a verb chain stays in the backend, collected only at a
  boundary; `coerceInputs` materializes a ref centrally so consumers were untouched;
  `collectPreview` makes a verb card a head-N preview (`FrameValue.__totalRows` carries
  the true count). The materialization bridges (Build/Split/Get Column/Get Row/Add
  Column), Pivot, Frame Lookup, and the cube ops (Nest/Unnest) stay eager JS — they're
  inherently materialization points. NOTE the win is bounded by the EAGER Rust engine
  (each verb still materializes a full DataFrame in Rust); true lazy-plan fusion + a
  direct CSV→Polars reader are the future scale steps.
- [x] Preview plumbing — `CableInspector` / `FrameDisplay` / `FrameChip` already
  render the `FrameValue` the nodes still emit; no change needed until the lazy
  step, when they switch to `backend.preview`. (`engine_collect` is the
  transitional full-materialize; `engine_preview` is ready for that step.)
- [x] Persistence — verified: source nodes persist `frameText` / sources (not
  handles), and verb nodes persist their params; handles are created + dropped
  inside each `data()` call (session-scoped, never serialized). A saved graph
  rebuilds identically. `persistence.ts` unchanged.

**Exit criteria:** on desktop, a chain of frame nodes composes a single Polars
plan and materializes only at previews; the same graph on web runs the JS backend
identically (smaller data). `tsc` + `vitest` green; a new `frameBackend.test.ts`
runs the verb suite against `JsFrameBackend`.

## WS3 — The relational verbs + Cube bridge (Phase C)

With the engine in, ship the **full** verb set (author decision: v1.0 is the
complete relational surface, not just plumbing). Each verb is a node whose
`data()` is one `backend.apply(handle, verb, params)`.

> **Progress (2026-06-25): the pure verb ENGINE is built + tested** —
> `frameVerbs.ts` implements all of select / drop / rename / sort / distinct /
> head / filter / groupBy / **join** (4 hows, null≠null) / append / pivot /
> unpivot / **nest** / **unnest**, reusing `compareOp` + `forAggregate` so they
> can't drift from the nodes. This is the JS backend's `apply` + the Polars
> parity oracle.
>
> **UPDATE (2026-06-26): the verb NODES are all built, registered, AND on the
> backend.** Reconciled against the code: `nodes/frame.ts` already has a node for
> every verb (Distinct / Head / Sort / Filter / Join / Select / Drop / GroupBy /
> Pivot / Unpivot / Append / Rename / Build / Split / Get-Add Column / Get Row /
> Nest / Unnest), each registered in `nodeCatalog.ts` (the Add menu + Function
> Reference). They now route through `frameBackend()` (the WS2 migration above),
> so the verb runs in Polars on desktop. **WS3 is effectively DONE:** frame XLOOKUP
> shipped (Frame Lookup node); cube-awareness was DECIDED (flat verbs do NOT map over
> nested cells — Unnest/Nest explicitly). Only a cube-cell XLOOKUP remains, and it's a
> v1.1 nicety, not a 1.0 blocker.

**Flat verbs — split into FOLD-IN vs NET-NEW (verify each against the code):**
- **Fold in / re-target onto the backend (already exist, do NOT rebuild):**
  - **Filter** — `FilterNode` in `nodes/list.ts` (catalog `list-filter`, label
    FILTER). Already keeps list values **or table rows** on one/two comparisons
    (AND/OR) or a keep-if mask. Re-target its frame path through `backend.apply`;
    keep the scalar/list path eager.
  - **Sort** — `SortNode` (`list-sort`), **XLookup** — `XLookupNode`
    (`nodes/lookup.ts`), **Get/Add Column**, **Slicer**, **1-D Group By**,
    **Build/Split Frame**: same treatment — reconcile their frame behavior onto
    the backend interface; the existing eager logic becomes `JsFrameBackend`.
- **Net-new verbs:** **Join** (the keystone — inner / left / right / outer, key
  match, schema merge, fan-out), **Group By** on a frame (generalizes the 1-D
  one), **Append / Union**, **Distinct**, **Pivot / Unpivot** (long ⟷ wide;
  pivot aggregates), **Rename**.

**Nest / Unnest — the flat ⟷ nested (Cube) bridge** (author 2026-06-25)
- [x] **Nest** — group one flat frame by key into cells (→ Cube). DONE —
  `frameVerbs.ts` `nestFrame`, node `NestNode` (eager; cube ops aren't Polars verbs).
- [x] **Unnest** — Cube → flat joined table (the inverse). DONE —
  `frameVerbs.ts` `unnestCube`, node `UnnestNode` (eager).
- Already shipped (v0.9): **Nest Join** (Join + Nest fused), **Build Cube**, the
  cube/frame-aware **INDEX**, drill-in `CubePopup`. Distinct axis from
  Pivot/Unpivot: nest/unnest changes **nesting depth** (lossless); pivot/unpivot
  changes **orientation** (stays flat).

**Cube function extension** (the "extend Cube" pillar)
- [~] **XLOOKUP frame/cube mode** — frame mode DONE 2026-06-26: the **Frame
  Lookup** node (`FrameLookupNode` in `nodes/frame.ts`, catalog `frame-lookup`,
  verb `lookupFrameCell` in `frameVerbs.ts`, tests `frameLookup.test.ts`). Finds
  the first row whose "In column" cell equals the Lookup value (type-aware: string /
  number / date-serial-or-ISO / logical), returns that row's "Return" cell on an
  `any` output; a miss → If-not-found (numeric-looking → number) else `#N/A`. Like
  Get Column it's a materialization-boundary op (eager JS on the already-materialized
  frame), not a Polars verb. **v1.1 niceties (NOT 1.0 blockers):** (1) the **cube-cell**
  half — lookup into a Cube returning a nested cell; (2) approximate match + a typed
  read-as output (the `any` output is the v1 simplification).
- [x] Cube-awareness of the flat verbs — **DECIDED: flat verbs do NOT auto-map over
  nested cells.** A flat verb operates on the flat frame; to act on a cube's cells you
  **Unnest → verb → (re-)Nest** explicitly. No implicit per-cell mapping / polyform
  pipeline. (Reaffirmed several times; keeps the verb semantics one-level and legible.)

**Legibility throughout** (the reason WS1 came first)
- [x] Schema-aware inspector, per-step row counts, an inspectable result at every
  node — DONE: `CableInspector` + `FrameDisplay` render each frame; `FrameChip`
  shows `[R×C]`; a verb card is a head-N preview via `collectPreview`, with the true

**Test data / seeds — author-owned.** The author plans to build a seed or two +

author's. The agents should keep `frameBackend.test.ts` fixtures in sync with
whatever shape that data lands in.

**Exit criteria:** every verb above exists as a node, composes into the Polars
plan on desktop (and the JS backend on web), and shows a preview + row count at
each step; the author's relational seed loads and is inspectable end to end.

## WS4 — GPU renderer (Phase D) — LANDED via the HTML-in-Canvas pivot

**Status (2026-07-01): DONE by a different path than planned below.** The WebGPU/
Pixi/MSDF approach in the phases below was **superseded** (2026-06-26 renderer
pivot — see dev-notes "Renderer pivot — HTML-in-Canvas"). Instead of re-drawing the
nodes in a GPU pipeline, the shipped renderer hands the browser the REAL node DOM and
draws it into a `<canvas>` via the WICG HTML-in-Canvas API (`ctx.drawElementImage` /
`canvas.layoutSubtree`) — crisp at any zoom, zero component re-authoring. It's built
(`htmlCanvasRenderer.ts`, `components/HtmlCanvasLayer.tsx`, `renderMode.ts` `"html"`
mode), feature-gated behind a Settings toggle (`Settings.tsx` RendererSection,
`supportsHtmlInCanvas()` detects `ctx.drawElementImage`), with the **DOM renderer as
the permanent default/fallback**. The API is behind `chrome://flags/#canvas-draw-element`;
the desktop build now enables it via `additionalBrowserArgs`
(`--enable-blink-features=CanvasDrawElement`) so the toggle unlocks on a WebView2
runtime that ships the feature. WS4 never gated the ship (DOM fallback), so this is
upside. The original WebGPU plan is kept below for the record.

Plan is **finalized** in `renderer-plan.md`; this section is the execution hook,
not a re-decision. Target = **WebGPU in the webview, WebGL2 fallback**, hybrid
(DOM only for the actively-edited node), **feature-gated with the rete DOM
renderer as a permanent fallback.**

**On "wgpu" (author's word) vs the plan:** same effort. The plan writes to the
**WebGPU browser API** (or Rust **`wgpu`**) — one shader/geometry codebase that
dispatches to Vulkan/DX12/Metal. In-webview WebGPU keeps the whole React/Vite/
Tauri stack; **native `wgpu`** is the recorded escape hatch (a native window
composited with the webview, reusing these shaders) *only if* Linux-desktop GPU
ever becomes a hard requirement. We are Windows-only now, where WebView2 =
Chromium, so in-webview is the path. (If the author means native-`wgpu`-from-day-1,
that's the one open decision below — flagged, not assumed.)

**Phases (SUPERSEDED by HTML-in-Canvas — kept for the record; DOM fallback intact throughout)**
- [ ] **Phase 0 — de-risk harness.** Render-mode store (`dom` | `canvas`,
  persisted, default `dom`) + GPU capability probe (`navigator.gpu` →
  `requestAdapter`, else non-software WebGL2). A transparent canvas overlay that
  mirrors rete's pan/zoom transform exactly — proves the coordinate math before
  drawing anything. No visual change.
- [ ] **Phase 1 — cables → one canvas/WebGL layer.** Most isolated, highest
  value. `cablePaths.ts` geometry reuses as-is; only the SVG emit in
  `ConnectionComponent.tsx` is replaced. May move the needle alone (nodes stay
  DOM).
- [ ] **Phase 2 — node bodies at LOD** (instanced quads + MSDF text zoomed out;
  real DOM component near 1:1 and for the active node). The compositing win.
- [ ] **Phase 3 — selection / drag / hit-testing on canvas** (spatial index),
  retiring the remaining `rete-area-plugin` interaction paths.

**Scope guard (from `renderer-plan.md`):** swap the **render + area** layer only
(~21 plugin-coupled files). **Keep untouched:** `NodeEditor`/`ClassicPreset` node
model, `DataflowEngine`, the value model, formula engine, all ~150 node `data()`,
persistence, groups/standoffs/conduits *logic*.

**Verification before Phase 1 (cheap):** a Chrome perf trace confirming Composite
Layers / Update Layer Tree dominates the zoom frame; confirm the probe routes
*software* WebGL2 to the DOM fallback.

**Greenlight rule:** start Phase 0/1 only when zoom-at-scale is a **real blocker**,
not a stress-test annoyance. Phases 2–3 only if 1 doesn't suffice. So WS4 can
legitimately lag WS2/WS3 in calendar time even though it's independent.

## Cross-cutting concerns

- **Browser-demo vs desktop split is load-bearing** (`compute-architecture.md`).
  The web demo stays the thin free funnel on eager JS; the desktop app is where
  native Polars (and later solver/sweep) lives. The `FrameBackend` seam is what
  keeps both alive from one node layer — protect it.
- **Solver / sweep (Monte Carlo, Goal Seek, Data Tables)** is the *other* native
  justification in `compute-architecture.md`, and the one with the genuinely
  chatty-border problem (batch a graph chunk to Rust, repeat over there). It is
  **NOT in the v1.0 Phase A–D scope.** Leave a forward hook (the IPC command
  surface should not preclude a "run this subgraph N times" command) but do not
  build it for v1.0 unless the author pulls it in.
- **Testing.** `vitest` env is `node` (no DOM) — so WS2/WS3 logic is unit-tested
  against `JsFrameBackend`; the Polars backend gets Rust-side tests + a parity
  test (same verb, same result, JS vs Polars) on a fixture. WS4 is verified by
  the author on the Vercel/desktop build (per CLAUDE.md — no puppeteer).
- **Keep `working` green throughout:** `tsc` + `vitest` after every step; push to
  `working` for the author to eyeball.
