# v1.0 execution plan — WS2 FrameBackend rationale

The full four-workstream 1.0 plan (WS1 Tauri spine, WS2 Polars engine, WS3 verbs + Cube
bridge, WS4 GPU renderer) shipped; its checklists are in git history. What's kept is WS2's
**central design decision** — the `FrameBackend` seam and why per-node IPC is fine — because

## WS2 — Polars relational engine (the keystone)

The real cost was an **engine-model change, not a dependency add.** A frame cable used to
carry a fully-materialized `FrameValue`; the target: data **lives in the engine**, a frame
cable carries a **lazy handle** (an opaque id for a Polars `LazyFrame` plan), and only at
*display* does a node collect a **preview** (schema + head-N + row count) across IPC.

### The central design decision: a `FrameBackend` interface (two implementations)
Do **not** scatter `isDesktop()` branches through ~30 frame nodes. Introduce one seam:

```
interface FrameBackend {
  source(spec): Promise<Handle>                     // literal / CSV / web → handle
  apply(h: Handle, verb, params): Promise<Handle>   // compose plan (cheap)
  preview(h: Handle, n): Promise<Preview>           // schema + head-N + rowcount (collect)
  column(h: Handle, name): Promise<TypedColumn>     // materialize one column
  drop(h: Handle): void                             // free the plan/handle
}
```

- **`JsFrameBackend`** (web demo + dev, and the parity **oracle**): a "handle" is the
  in-memory `FrameValue`; `apply` runs the eager `frame.ts`/`frameVerbs.ts` logic;
  `preview`/`column` are near-identity. The web build keeps working unchanged (Polars has no
  production WASM path — `compute-architecture.md`).
- **`PolarsBackend`** (desktop): `apply` composes a `LazyFrame` plan via `invoke` (cheap — no
  materialization); `preview`/`column` call `.collect()` head-N in Rust. Handles are ids into
  a Rust-side `HashMap<HandleId, LazyFrame>`.

The backend is chosen once at startup (`initFrameBackend()`: desktop + `engine_ping` reports
`"polars"` → Polars, else JS). Every frame node speaks the interface; the swap is one module.

### The sync → async wrinkle (called out early)
`DataflowEngine` is push-based; `node.data()` may return a Promise (rete awaits it), so
**frame `data()` methods become async**. The scalar/list/number/formula layer **stays eager
JS** — only the frame layer goes handle-passing/async. The boundary is exactly where a handle
↔ a materialized value:
- **Get Column / Get Row** materialize (handle → typed list/row) — the bridge back to eager.
- **Build Frame / a list-into-frame widen** (`coerceInputs.ts`) materialize the other way.

### "Don't chat across the border" — why per-node IPC is fine
`compute-architecture.md` warns against chatty borders — but that's about **per-element /
per-iteration** messaging (the solver/sweep case), NOT per-node plan composition. Lazy
`apply` calls carry no data and don't materialize, so one small message per frame node is
cheap; we materialize **once** per visible preview. Keep it that way: never collect except
for a preview or an explicit `column`/`row` bridge.

(How it actually shipped: a first transitional collect-full-per-verb migration merged
2026-06-30, then the lazy-`FrameRef`-on-cables finish, then lazy-plan fusion — see the "What's
working" relational-engine entry + dev-notes history.)
