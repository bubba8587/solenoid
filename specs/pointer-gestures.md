# Spec: Pointer gestures

Serves [[C92]] pinchUnvetoable (where each gesture listens and what counts as a finger), [[C93]] gestureByPointerType (what a finger, a mouse and a pen each do) and [[C43]] oneFlowSurface (both canvases wire the gestures once). It covers what the system does and blocks, and the decision each behavior serves. A WHY that isn't in a node belongs in one.

**The rule ([[C92]]): pinch listens in CAPTURE and cannot be vetoed; pan and node-drag listen in BUBBLE and can be.** Both halves matter — do not move either. React Flow's node drag (d3-drag) and pane pan bind in bubble on the node/pane element, so wrapper CAPTURE listeners that consume multi-touch moves out-prioritize them — no component's `stopPropagation` can hide a finger from the pinch, while a control that wants the pointer for itself (a slider, a dial, a text field) can still suppress the pan and the drag by stopping the event. Only the zoom is unstoppable. (The rule predates the RF cutover — rete's stock `Zoom` counted fingers in bubble and any swallowed pointerdown killed the pinch for the whole gesture; the fix was positional then and stays positional now: no call site can break a pinch, and none has to remember not to.)

**`installFlowPinch` (wrapper capture, TOUCH events).** Touch events, not pointer events — multi-finger input is only reliably enumerable there (d3 listens the same way). Two touches on `touchstart` arm the gesture; each two-touch `touchmove` is consumed (`preventDefault` + `stopImmediatePropagation`) so RF's bubble handlers never see it, and drives the viewport directly: the world point under the start centroid stays pinned, the pan follows the centroid, zoom clamps through `clampZoom`. A third finger disarms. **A pinch never selects:** finger 1 may land on a card before the gesture is classifiable, so gesture end arms a ~400ms capture-phase click guard that swallows the click that finger would otherwise deliver — prevented, not rolled back (rete's "pinch also SELECTED whatever finger 1 landed on" bug; rollback was rejected there because correcting a visible wrong state reads as a glitch).

**`installTouchCardPan` — the one-finger rule on touch ([[C93]] gestureByPointerType).** A one-finger drag on an UNSELECTED card or group PANS the canvas — a busy graph leaves no blank pixels to pan from otherwise. A SELECTED node drags (tap-then-drag); mouse and pen keep select-and-drag in one motion (the model keys on POINTER TYPE, not device class). The claim test: inside `.react-flow__node` without `.selected` (RF stamps it synchronously — the one source that's true at pointerdown time), not on a discrete control (`button, select, .react-flow__handle, [data-socket-key]`); text fields deliberately do NOT veto — a tap still focuses them, but a drag from one pans. No `preventDefault`, so the tap's click survives and tap-select keeps working.
- **The qualifying press must be stopped at `touchstart`, not just `pointerdown`** — d3-drag binds `touchstart.drag` in bubble on the node element, so the pointer-stream stop never reaches it. Unstopped it only LOOKS still in pan mode: the pan tracks the finger 1:1, so the drag's flow-coordinate delta cancels to zero — and the bug surfaces the moment panning is off (select mode).
- A second finger hands the gesture to `installFlowPinch` mid-drag (`touchCount()` governs).

**Touch-select mode (`touchSelectStore`).** While on, RF's `multiSelectionActive` store flag is held true (taps toggle cards in/out of the selection — rete's "Ctrl held" semantics), `panOnDrag` is off while `IS_COARSE && touchSelect`, and the card-pan gesture goes dead on unselected cards (no pan, no drag — the tap's click still toggles).

**What counts as a finger — the census (`pointerGesture.ts`).** A module singleton on **window capture** (self-installing on import) — the only listener position that is both global and un-swallowable. A contact counts as a finger when its `pointerType` is neither `mouse` nor `pen` — an UNKNOWN or absent `pointerType` counts as touch (pinned by `pointerGesture.test.ts`); `isPinching()` = **≥2 such contacts**, `touchCount()` the number, and everything that yields to a pinch reads from here — never count raw pointers (a resting stylus or a mouse in contact is not half a pinch). `resetPointerCensus()` is the backstop for a `pointerup` the browser never delivers (long-press contextmenu, a pointer that leaves the window).

**No palm rejection, deliberately ([[C93]]).** Solenoid is a precise editor, not an inking surface: nobody rests a palm on a node graph, so there is no palm to reject and the state that would take isn't earned (author call, 2026-07-27). A pen is handled only as what it is — a *precise* pointer: it never counts toward a pinch, and it keeps select-and-drag in one motion like a mouse. If a drawing-style surface ever lands in the app, this is the decision to revisit; it would want contact geometry (`width`/`height`/`pressure`), not a pen-active flag.

**Tablet.** `IS_MOBILE` is false on a tablet (iPadOS ships a desktop UA by default — deliberate, see `coarse.ts`), so a tablet runs the desktop CHROME. The gesture model keys on pointer type, so touch behaves exactly as on a phone: tap-then-drag on unselected cards, two fingers zoom over any pixel.

**Both canvases ARE one surface ([[C43]] oneFlowSurface).** The main canvas (`FlowCanvas`) and the composite drill-in (`FlowCompositeOverlay`) render the same `FlowSurface`, which wires `installFlowPinch` + `installTouchCardPan` + `installWheelZoom` (and the lasso, menus, keyboard) once — anything installed in a host instead of the surface is a behavior the other silently lacks (the rete-era dead drill-in finger pan, and the RF-port dead drill-in lasso / hotkeys / group collapse, all came from exactly that).

**Locking is CSS plus RF props.** Both surfaces apply `.solenoid-canvas--locked` on their wrapper (sets `pointer-events: none` on node chrome / sockets / cable hit-paths) and pass `nodesDraggable={!locked}`. Keep the mirror on both; dropping the drill-in's class would leave a locked drill-in's fields and sockets editable. A single group's position lock is separate and finer-grained: `toFlowNodes` emits per-node `draggable: false` for a `lockedPosition` group (RF overrides the board-wide `nodesDraggable` per node), and `syncTopology` compares `draggable` so a lock toggle re-projects; resize is a custom grip, not RF drag, so it stays live.

**In-canvas opt-out classes — `.nowheel` / `.nodrag` / `.nokeys`.** A figure that owns its own scrolling or keyboard carries these on its root so the canvas gestures stand down for a press or focus inside it. `.nowheel` (capture-phase guard in `flow/flowWheel.ts`) lets a wheel scroll the element instead of zooming the canvas; `.nodrag` is React Flow's own (a press there doesn't drag the node). `.nokeys` (`canvasKeyboard.ts`, the keyboard mirror of `.nowheel`) makes the canvas key handler return for any event whose target has a `.nokeys` ancestor, so a focused grid cell's arrows don't nudge nodes and its letters don't open the Add menu or Tidy — **F9 still recomputes** (the one exempt key, like the modal/presenter/drill gates). The Gantt figure's tree grid (`role=treegrid`) carries all three; a single-`<svg>` chart needs none.

**`stopDragStart` (`coarse.ts`) decides the ONE-finger question only:** does a drag starting on this element pan/drag the canvas, or belong to the element? Node chrome and single-line fields use it. Two groups keep an unconditional `stopPropagation` for established reasons: drag-interactive controls (sliders, dials, the Conduit, group bodies, resize handles) genuinely own the pointer, and `<textarea>`/contenteditable own their own scroll and text selection. Native-popup controls (`<select>`/`LazySelect`, `<input>` of type color/date/file) also keep the swallow — it doubles as drag prevention, and on rete it was load-bearing for the popup itself (a selection re-order reparented the node element and closed the open dropdown; that DOM-move mechanism died with the rete surface, but the swallow costs nothing and keeps a press on a small control from starting a pan). Pinch is unaffected by any of these — the capture-phase count doesn't care what they swallow.
