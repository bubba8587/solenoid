## Decision

One format model decides what a Format Controller renders. The adopted socket type maps to a family, and the family decides which controls exist. A control outside the family is hidden in the popup and inert when the format resolves: never disabled-but-visible, and never silently applied. Precision resolves by one shared rule across every number style, with no precision logic private to a style. The unit is independent of style: every number style accepts a unit, and no other family takes one.

## Why

The model replaced a hand-written switch per style, with precision duplicated in each case, and a popup gated by scattered `isDate`/`isText` checks. Every new style or family was another place for the two halves (what renders and what the popup shows) to disagree. Controls are hidden rather than shown disabled because an absent control is not a fact worth showing. The one sanctioned disabled control is the unit dropdown under a lock, because there the value does have a unit and the control shows whose it is ([[C25]] firstClassUnits).

## Consequences

- The family table, the control truth table, the advanced tier and the complex rules are in [[format-model]]; `formatModel.test.ts` checks the whole `SocketDataType` union against it.
- Frames are `none` in this model: per-column unit and format are a separate representation, not a scalar annotation stretched over a table ([[D43]] unitByGranularity).
- An FC never re-defaults its style pick when its socket type changes; a pick outside the current family is inert until a fitting type returns (`effectiveFormat`). A value typed only at run time, such as a Script output, passes through a wildcard and then its construction-time family before its real type arrives, and re-defaulting on each hop destroyed a saved date style.
- **Reopen if:** a control needs a disabled-but-visible state for a reason other than a lock, or a family needs two precision rules.
