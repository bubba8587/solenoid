## Decision

A unit is part of a value: 5 m and 5 km are different values, so relabeling a unit would be overwriting the number. Only Convert, or a calculation whose result is a different kind of quantity, changes a unit; a Format Controller after a value that already has a unit shows it and can't change it. Values with units compare by their actual quantity, so 5 km matches 5000 m, and a currency is known by its code, so $5 never matches 5€.

## Why

We want a value to know what it is ([[B17]] typedValueModel), and a number's unit is part of that. A unit that a dropdown could relabel would make every number with a unit untrustworthy.

## Consequences

- A unit the user types in (say, "widgets") is a kind of quantity of its own, never a plain number, so widgets per second never reads as Hz. Two typed names that differ only in case are the same unit.
- A Convert further along fills in a Format Controller's unit only when the Format Controller has none. A unit the user set stands, and a real clash shows as the Convert's error rather than a silent rewrite.
- A node that doesn't do unit math only ever sees plain numbers: [[compute-pass]] (Arrival coercion).
- How it's built: [[unit-flow]].
- **Reopen if:** nothing; a unit that could be relabeled is a wrong number.
