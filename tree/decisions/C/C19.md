## Decision

**MUST:** a node shows the user exactly these names, and each one comes from a single place and nowhere else.

- **Name:** the node's name in the Add menu, or for a node with an operation picker, the chosen operation's name. A label the user types wins. It is how the node is named everywhere: its title, the Navigator, the Inspector, Problems, Pins, Comments, the status bar, Isolate, the cable inspector, history and popup titles. The title rules are [[D22]] oneNamePerCard.
- **Family name:** shown only in the hover hint on the node's type, under the exception in [[D22]].
- **Excel names:** shown in the Inspector, at the end of the description ("Excel: X."), and in Add menu search as a row that shows the name ("Table Size: ROWS") whenever it isn't already the row's own name or one of its operations.
- **Operation names:** the operation picker, the search rows for operations ("Host: Op"), and the title when an operation has its own menu entry.
- **Formula name:** the name the formula bar accepts; letter case per [[D23]] capsClaimsFunction.
- **Socket labels:** the node's rows, as bare nouns, with longer hints on hover.
- **Description:** the menu row, the header hover and the Inspector; voice per DESIGN.md §7.

Names that exist only in the code are never shown.

## Why

[[B16]] oneFormulaSurface gives a function one name on the formula bar and on the canvas. The same has to hold for every name a node shows, because a user reads a name in one place and looks for it in another. When each surface picked its own source they disagreed: one node was "Table Size" in the menu and "Table Info" on hover, and a search for ROWS returned a row that never said ROWS.

## Consequences

- Where each name is stored and how every surface reads it: the Add menu spec, *Where each name comes from*.
