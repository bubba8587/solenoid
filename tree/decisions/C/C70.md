## Decision

The schedule is always recomputed from the table, and four visible columns carry one rule each:

- a typed **Start** holds a task to start no earlier than that date;
- a typed **Finish** caps the task's late finish, and a task that runs past it shows negative float;
- a **Deadline** flags a task and never moves it;
- **Manual** pins a task in place, and the pinned task still drives its successors.

A gap between two tasks is a lag on the link between them. There are no constraint-type columns, no per-task scheduling mode and no project-wide shift switch.

## Why

The top complaint about scheduling tools in the user sweep was dates moving because of state the user could not see. Four visible columns with one rule each leave nothing hidden.

## Consequences

- A structural failure (a cycle, an unknown predecessor name or a duplicate name) aborts the whole run with one error that names a member; a per-row fault (a bad duration, an unparseable date) stays on its row. No task in a loop has a defined start, so nothing downstream of one does either.
- **Reopen if:** an imported file needs a constraint the four columns cannot express (as late as possible, must finish on). Even then it becomes a named `unsupported` entry at the MSPDI border ([[D68]] importUnsupportedIsNamed), not a fifth column.
