## Decision

Solenoid uses an mdbase schema in two places and no more:

- Vault Folder takes a column's type from the folder's mdbase schema first, before Obsidian's own property types and before guessing from the values.
- Write Properties refuses to write a row that breaks one of the schema's rules (wrong type, a value not on the allowed list, below a minimum or above a maximum, a required property missing).

Both do nothing when the folder has no schema, and a schema Solenoid can't read falls back to guessing rather than refusing the folder. That is the limit: Solenoid writes no schema files of its own and doesn't run queries through the mdbase tool (parked).

## Why

mdbase is an optional schema file that sits beside a folder of notes; it is not how TaskNotes stores its data. TaskNotes writes ordinary note properties, which Solenoid reads whether or not a schema exists, so the [[B1]] obsidianBet integration only needs to respect a schema when one is present. mdbase may still change in breaking ways before its 1.0, so a schema Solenoid can't read must never block a folder.

## Consequences

- A user can write one schema that serves both Solenoid and TaskNotes, and it works today.
- The pitch leads with Obsidian and TaskNotes; mdbase gets one clause ("respects an mdbase schema when the folder has one").
- Which files and rules are read: `docs/node-coverage.md` § Vault Folder and Write Properties.
- **Reopen if:** mdbase reaches 1.0, or users arrive with schemas and ask for more. A schema writer would then be about the size of the existing `.base` writer.
