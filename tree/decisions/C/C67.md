## Decision

Solenoid uses an mdbase schema in two places and no more:

- Vault Folder types a column from a matching mdbase type first (`mdbaseTypes.ts`), ahead of `.obsidian/types.json` and the type guesser.
- Write Properties refuses a row that breaks a type, enum, min, max or required rule (`mdbaseSchemaFor` and `validateAgainst` in `mdbaseTypes.ts`).

Both fall through silently when the folder has no schema, and an unreadable schema falls back to the guesser rather than refusing the folder. That is the ceiling: Solenoid writes no type files of its own, has no type-file writer beside the `.base` writer, and passes no queries through to the mdbase binary (bundle item H, on hold).

## Why

mdbase is an optional schema file that sits beside a folder of notes; it is not how TaskNotes stores its data. TaskNotes writes ordinary frontmatter, which Solenoid reads (through the plugin's API or from disk) whether or not a schema exists, so the [[B1]] obsidianBet integration only needs to respect a schema when one is present. The mdbase spec may break before its 1.0, so a schema Solenoid cannot read must never block a folder.

## Consequences

- A blended Solenoid and TaskNotes `_types/` schema is the user's to write, and it works today.
- The pitch leads with Obsidian and TaskNotes; mdbase gets one clause ("respects an mdbase schema when the folder has one").
- **Reopen if:** mdbase reaches 1.0, or users arrive with schemas and ask for more. A type-file writer would then be about the size of the `.base` writer.
