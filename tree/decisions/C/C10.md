## Decision

A value never changes kind on its own; that takes a Cast node, except between true/false and numbers. A value always fits where a bigger shape is expected, and a smaller shape takes a node that picks what to keep. So a formula never turns text into a date, number or logical, even when it looks like one: text becomes another type only in a typed input, where the type shows on screen (a column's type, a socket's color, a Date field), or when the formula asks for it with a converter (DATEVALUE, TIMEVALUE, NUMBERVALUE or VALUE), and both read text the same way. The text tests (Contains, Starts with, Ends with) work only on text: on a number, date or true/false they answer an error that says to turn it into text first.

## Why

A value's kind and shape are part of what it is, so neither changes quietly. Growing a shape loses nothing; shrinking one has to drop something. A guess you can't see is a wrong answer you can't see: a formula that quietly turned "3/1/2024" into a date would hold a type nobody chose. This breaks deliberately from Excel, which reads `="5"+1` as 6. A number turned into text depends on how it happens to be printed, so a text test on it would make a format change look like a data change.

## Consequences

- Arithmetic on text is `#VALUE!`, and `5 = "5"` is FALSE ([[formula-language]]). A function reading a range or list takes text as text: it doesn't read `"5"` as 5, and an aggregate that skips non-numbers skips it.
- *Exception:* IMSUM, IMABS and the rest of the complex-number functions read text such as "3+4i", since text is how Excel writes a complex number. **Removed by:** a typed complex input that people use in its place.
- *Unenforced:* a criterion string (COUNTIFS, SUMIFS and kin) still reads a date out of its text as Excel's criteria do; replacing Excel's criterion syntax is in the backlog (`docs/backlog.md` § Leaves the code breaks).
- How it's built: [[socket-lattice]], and the text tests in [[frame-verbs#filter and filterMulti]].
- **Reopen if:** a new kind of value arrives; a second automatic crossing between kinds is wanted; a typed input can't express a value people need to type into a formula; or people want text tests on numbers and accept one fixed printing for them.

## Contest

### Contest 2026-09-26 by claude: keep wins

keep: kinds never mix and shapes widen only upward is B17 applied to connections; both rules are cheap and derivable. opposite (automatic kind crossings, or narrowing) converts behind the user's back, which B17 forbids. deletion leaves every connection pair to be hand-listed, which B17's 'nothing converted silently' cannot decide pair by pair. Keep.
