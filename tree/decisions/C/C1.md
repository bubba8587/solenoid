## Decision

The app ships a read-only demo vault (`demoVault.ts`, `demoVaultData.ts`) under the sentinel root `solenoid:demo-vault`. The path-aware `fs()` dispatch in `fileBridge` sends any path under that root to an in-memory provider, so the vault readers work with no real filesystem, and every write there throws. The demo files are lazy-loaded and stay out of the main bundle.

The same seam serves Local File's data folder: while a marketing page forces the demo, `getCsvFolder` resolves to the demo vault's `Data` folder, so Local File reads a bundled CSV on the web. Parquet still needs the native engine.

## Why

[[B1]] obsidianBet needs the vault integration to be demoable, and [[B2]] webTryDesktopFull needs the demo to work on the web, where there is no filesystem. Routing by path leaves desktop file operations on the real filesystem untouched. Extending the seam to Local File lets the Excel-over-CSV marketing scene read a real bundled `expenses.csv` instead of a mockup.

## Consequences

- Which vault a node reads (the one a marketing page forces, a configured one, or the demo) is [[D62]] demoVaultResolution.
- The sentinel root carries a colon, so it can never collide with a folder path a user could type. The marketing pages' force switch pins the vault root and the data folder together and is never persisted. On the dev server the demo files are read live from disk (`/__demo-vault`, `vite.config.ts`), so an Obsidian edit to the repo's vault shows on refresh.
