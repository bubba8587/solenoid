## Decision

Table operations (filter, join, group, sort and the rest) run on Polars, a fast native engine, in the desktop app, and on a plain JavaScript version that gives the same answers in the browser. DuckDB is not used, and no second engine is added for the web without reopening this.

## Why

The web is for looking and trying and the desktop is the full product ([[B2]] webTryDesktopFull), so the fast engine belongs on desktop, and the web only needs something that gives the same answers.

## Consequences

- Keeping the two engines giving identical answers is a permanent cost, paid in shared test cases both must pass. How it's built: [[frame-verbs]].
- **Reopen if:** a production-ready Polars for the browser appears, or the web becomes a full target. DuckDB on both is the alternative in reserve.

## Contest

### Contest 2026-09-24 by Claude Opus 5.5: keep wins

Judged by B2. Keep: web stays instant and filesystem-free on the oracle, desktop gets native speed; the cost is parity upkeep, which D29's corpus and fuzzer make mechanical (8 divergences found and closed 2026-09-24). Opposite (DuckDB on both, wasm on web) adds a multi-megabyte web download against B2's look-and-try web and SQL semantics that differ from the Excel-parity oracle. Deletion (the JS oracle everywhere) forfeits the desktop full product's scale. Variant (Polars-WASM) has no production path yet, which is already this node's reopen trigger.
