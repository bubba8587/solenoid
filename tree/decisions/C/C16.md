## Decision

The relational verbs run on native Polars on desktop and on the JS oracle (a pure JavaScript implementation that gives the same answers) on the web, behind the `FrameBackend` seam. DuckDB is not used, and no second engine is added "for web" without reopening this decision.

## Why

[[B2]] webTryDesktopFull makes the web look-and-try and desktop the full product, so the full engine belongs on desktop, where native Polars runs, and the web needs only an oracle that gives identical answers.

## Consequences

- Standing risks: Polars API churn (pinned at 0.46), softened by the seam, by the JS oracle as the reference, and by the cargo parity tests ([[frame-verbs#The parity corpus]]). Keeping web and desktop in parity is a permanent cost; budget for it.
- **Reopen if:** a production Polars-WASM path appears, or the web becomes a full target. DuckDB (one engine for both targets) is the scoped alternative, and the seam makes that swap one module.
- The native store recovers a poisoned lock and runs every verb outside the lock on a cheap clone of the frame. A panic deep in Polars would otherwise fail every later engine call until the app restarts, while the webview keeps running, and one long verb would stall every other call. The store is only a handle map, so its data is valid wherever a panic unwound.

## Contest

### Contest 2026-09-24 by Claude Opus 5.5: keep wins

Judged by B2. Keep: web stays instant and filesystem-free on the oracle, desktop gets native speed; the cost is parity upkeep, which D29's corpus and fuzzer make mechanical (8 divergences found and closed 2026-09-24). Opposite (DuckDB on both, wasm on web) adds a multi-megabyte web download against B2's look-and-try web and SQL semantics that differ from the Excel-parity oracle. Deletion (the JS oracle everywhere) forfeits the desktop full product's scale. Variant (Polars-WASM) has no production path yet, which is already this node's reopen trigger.
