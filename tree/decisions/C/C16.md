## Decision

The table operations (filter, join, group, sort and the rest) run on Polars, a fast native engine, in the desktop app, and on a plain JavaScript version that gives the same answers in the browser. DuckDB is not used, and no second engine is added "for web" without reopening this decision.

## Why

[[B2]] webTryDesktopFull makes the web look-and-try and desktop the full product, so the full engine belongs on desktop, where Polars runs, and the web needs only a version that gives identical answers.

## Consequences

- Standing risks: Polars changes its API between versions (it is pinned at 0.46). The risk is softened by keeping the engine behind one swappable boundary, by treating the JavaScript version as the reference answer, and by a shared set of test cases both must pass ([[frame-verbs#The parity corpus]]). Keeping web and desktop in step is a permanent cost; budget for it.
- **Reopen if:** a production-ready Polars for the browser appears, or the web becomes a full target. DuckDB (one engine for both targets) is the scoped alternative, and the boundary makes that swap one module.
- How it's built, including how the desktop engine survives a crash inside Polars: [[frame-verbs]].

## Contest

### Contest 2026-09-24 by Claude Opus 5.5: keep wins

Judged by B2. Keep: web stays instant and filesystem-free on the oracle, desktop gets native speed; the cost is parity upkeep, which D29's corpus and fuzzer make mechanical (8 divergences found and closed 2026-09-24). Opposite (DuckDB on both, wasm on web) adds a multi-megabyte web download against B2's look-and-try web and SQL semantics that differ from the Excel-parity oracle. Deletion (the JS oracle everywhere) forfeits the desktop full product's scale. Variant (Polars-WASM) has no production path yet, which is already this node's reopen trigger.
