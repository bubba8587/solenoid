## Decision

A formula never reads a type out of text on its own: text is text, even when it looks like a date or a number. Only
the input surfaces, which are typed and show the type they hold (a column header's type, a socket's color, a Date entry),
read text into a date, number or logical, one way ([[D93]] oneTextReading). A formula that wants a value from text says
so with an explicit converter, such as DATEVALUE, TIMEVALUE, NUMBERVALUE or VALUE, which reads it the way a typed input
would.

## Why

A guess you can't see is a wrong answer you can't see. The inputs are where the type is on screen, so that is where text
may become something else; a formula that quietly turned "3/1/2024" into a date would have a type nobody chose.

## Consequences

- Arithmetic on text is `#VALUE!`, and `5 = "5"` is FALSE ([[formula-language]]).
- A function reading a range or list takes text as text: it doesn't read `"5"` as 5, and an aggregate that skips
  non-numbers skips it rather than reading it.
- *Unenforced:* a criterion string (COUNTIFS, SUMIFS and kin) still reads a date out of its text as Excel's criteria
  do. Excel's criterion syntax is its own little language and the author finds it confusing; replacing it is in the
  backlog, and until then it keeps working as it does.
- **Reopen if:** a typed input can't express a value people need to type into a formula.
