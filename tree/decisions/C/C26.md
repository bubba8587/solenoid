## Decision

**MUST:** a node's choices are either ops or arguments, and the field name is the whole classification.

- **An op** is stored in a field named `op`, declared as a family in `NODE_OPS`, and picked with `OpSelect` or `OpToggle` at the top of the card, in the accent color. Each op is its own formula function and has its own Add-menu row.
- **An argument** is a parameter of the node's one function. It is stored under its own name (`side`, `order`, `agg`, `view`, `condition`), picked with a neutral `ArgSelect` or `SegToggle` in its own row, and has no formula name and no search row. Its search words go in the host leaf's `keywords`. On the formula surface it is a parameter of the host's function: `SORT(list, index, order)`, `RUNNING(op, list, [window])`, `PADTEXT(text, width, [side])`.

Nothing sits between the two: no `kind` switch, no `arg` flag, no argument family in `NODE_OPS`, no argument stored as `op`.

**An aggregator is an argument when the card has a job it only parameterizes.** Group By, frame Group By, Cube Rollup and Running each pick SUM, AVERAGE, MIN and so on under `agg`, and none of them names a function per aggregator. Aggregate is the exception: there the aggregator is the whole node, so it is an op family.

## Why

Ops and arguments used to share a field name (`op`), a component (`OpSelect arg`) and a declaration (`kind`), and every seam between them drifted. Argument families got the accent (Sort, Drop Blank Rows), classes with no picker declared `argument`, and display families were accented with nothing searchable (Gauge, Proportion). Pad's op field was named `dir`, so PADLEFT and PADRIGHT couldn't be searched. When the field name decides, there is nothing left to keep in sync.

Running shows the classification going wrong both ways. A per-op family, `RUNNINGSUM` through `RUNNINGSTDEV`, gave a parameter seven top-level names. Deleting the formula surface entirely then left the parameter with no function to sit inside. The author's call was `RUNNING(op, list, [window])`, the shape `SORT` already had. So a per-op formula name is never evidence that a family is an op; it follows from the classification and doesn't decide it.

## Consequences

- To classify a new picker, weigh the signals together instead of letting the last one win. Would the user pick it, or could it arrive computed? Does it have its own name? ([[C18]] uniqueNameMap can overrule: ops that would share a formula name can't be ops.) Would the user search for it? Is it meaningless without its host? Is it an Excel function? That last one only corroborates.
- Distribution's `.RT` forms have search rows because Distribution is an op family, not because arguments may be searchable.
- Gauge's Dial and Bar are an argument (`mode`, a SegToggle), not ops: nobody searches the Add menu for "dial" or "bar", and the card has no formula surface.
- Whether every op is callable from a formula is the parity program's business ([[C17]] shareImpl), not this rule's.
- The picker components and their layout are in `DESIGN.md` § Op pickers.
- **Reopen if:** users search for aggregator names and don't find them. The fix is then more `keywords` on the host leaf, not a search row per aggregator.
