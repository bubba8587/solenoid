## Decision

A list is one row ([[D85]] columnsStayColumns), so a Frame column, read whole in a formula, is a one-column table. Every function that takes a whole list declares, on its own entry, whether a vector's direction matters to it: a direction-free function reads a one-column or one-row table as its items and answers a list the way its first vector came in, and an axis-aware function (SORT, TAKE, VSTACK) gets the table as it is. A list wired into a computed column that has one value per row reads as a column too.

## Why

A list is one CSV row, so calling a column a list turned it sideways: ROWS(price) was 1, and SORT or TAKE worked across it. Making the column a column fixes that the way Excel's table columns work, but most list functions have no sense of direction and must not start failing on a column. Answering in the shape they were given keeps orientation from flipping mid-formula, which is what [[D85]] columnsStayColumns guards against: price / NORMALIZE(price) must divide column by column, not spread into a grid. A wired row-aligned list is per-row data like a column, so SUM(price * weights) stays element by element.

## Consequences

- The declaration is `orient` on the function's entry in `EXCEL_IMPL_META`, so any surface that hands a function a column gets the same reading. A test fails when a list-taking function has none.
- A Cube column whose cells hold lists is no single list, so it stays `#SHAPE!` read whole ([[D81]] cubeRowLists).
- **Reopen if:** a function needs direction for one argument and not another; the declaration then moves to the argument.
