## Decision

The author's words, 2026-09-26:

- "ok yep data blanks are blank."
- "wired setting input blanks I think should be an *overriding* skip- i.e. if I type a position 5 into INDEX, then wire a blank number input cable, that 5 is suppressed until the cable is removed."
- "formulas following the same rule: yes."
- "in almost no case I can imagine should we need to blank the entire result."
- A setting with no default: "we can use the #SYNTAX! error. already have that."
- "what I meant was that it *skips* the setting at that spot. the Way B behavior is more correct. my intention is to have as few blank results as possible. if we need to make a stink about something missing or blank, we should prioritize using #SYNTAX! to alert the user."
- "I think that a blank/skipped arg (and/or 0) resulting keeping the whole thing is a intuitive sub-rule in this domain. not something we have to chase, but works fine as a fallback behavior where applicable."
- "I think a half-built card erroring is fine? you could always put in default values if need be."

**MUST**, as built: a setting is an input that tells a node how to work on its data (a count, a position, a size, a mode). A blank wired into it, a blank value in its formula slot, or a blank item of a list of them reads as the setting left out, so the node uses its default; with no default, `#SYNTAX!` names it. An error still passes on ([[D35]] errorInErrorOut). A node whose data is wholly blank answers blank.

*Claude's reading, not yet the author's word:* in a pick list (INDEX's positions, CHOOSEROWS's indices) "skips the setting at that spot" drops the pick, so the answer is shorter than the list; a pick list of only blanks is the setting left out. A blank inside a table of positions still answers blank there (open: `#SYNTAX!` instead?).

## Why

[[D33]] keeps a wired blank from turning into a number nobody can see, which protects data. A setting is not data: a blank count is not an unknown count, it is a count nobody gave, and "not given" already has a meaning, the one a skipped formula argument has ([[C80]] blankArgIsExcelBlank). Blanking the whole answer instead throws away the table that was wired in and protects nothing. The card already hides the typed value while a cable is plugged in, so the override is visible (the author: "our node card design already suppresses typed inputs").

## Consequences

- *Excel diverges:* Excel reads an empty cell in a size slot as 0, so `TAKE(m, A1, 2)` with `A1` empty is `#CALC!` there; here it keeps every row ([[A6]] divergeByDesign). The author: "that's a fine divergence and I think it's a strict upgrade on Excel behavior in this instance".
- *Where:* cards read a setting through `readSetting` or `requiredSetting` (`nodes/shared.ts`); formulas declare their setting slots in `BLANK_ARG_TYPES` (`excelFormula.ts`), with `required` for a setting that has no default.
- *Not yet swept:* only TAKE, DROP, EXPAND, INDEX, ROUND and CHOOSEROWS/COLS follow this so far; the rest of the catalog is a backlog item ("this may need to be a large sweep/audit and sockets gain a declaration"), Filter's value among them, which overturns [[C24]]'s blank-filter consequence when it lands: "I don't really care about C24, it's fine to override and make compliant with other changes".
- **Reopen if:** a setting's default would surprise more often than a blank answer would.
