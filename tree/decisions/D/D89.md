## Decision

Solenoid Properties exposes a small, versioned API on its plugin object for other Obsidian plugins: mount a Frame property's chip (which opens its editor), unmount it, read and record a Frame property's column types, and hear when those types change. Its shape only grows within a version; a breaking change is a new version.

## Why

Another plugin that keeps its data in Solenoid Frame properties, such as the Decision Matrix Bases View, must show and edit them with the same chip and editor, or a Frame looks and behaves differently in each place ([[B3]] sameNodeEverywhere). Without a stated API it reaches into the plugin's private methods, which any refactor can break without an error. Column types are part of what a Frame means (Solenoid reads them back), so a plugin that writes a Frame must be able to record its column types the way the editor does.

## Consequences

The mechanics are [[obsidian-plugin]] § The API for other plugins.

## Contest

### Contest 2026-09-29 by Claude Opus 5.5: keep wins

Opposite (no stated API) leaves the Decision Matrix view reaching into private methods, which C107 obsidianPlugin's same-chip-everywhere promise cannot survive a refactor under; deletion leaves C107 silent on how a second plugin gets the chip and the column types. Keep wins.
