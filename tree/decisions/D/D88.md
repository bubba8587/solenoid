## Decision

A frame's Table popup has a Cards view: every row drawn as a card in one narrow column, for reading a frame on a phone. The grid is the truth and every popup opens in it; Cards is an option you pick. Nobody writes a card layout. It is worked out from the columns (their order, types, names and what the cells hold), so the same frame always gets the same cards. The same cards are also a Record view, so they can be drawn as a chart (a gallery in a Display, the chart popup or a Report), and the popup can add that Record node for you.

## Why

[[C63]] oneRecordNode puts every authored record view on the Record node and keeps data entry on the Form view, whose layout is written on the Frame Input. A grid of many columns is unreadable at phone width, and asking for a layout before you can read your own data on a phone is backwards, so this view is derived rather than authored. Deriving it the same way every time means a card never rearranges itself between opens.

## Consequences

- The Cards view reads; editing stays in Form, and on an editable popup each card jumps there.
- The Record node's Cards view has no layout to write; its other views keep theirs.
- **Reopen if:** people want to author the card layout, which would make it a Record view on the Record node instead.
