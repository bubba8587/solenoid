## Decision

**The shape model.** A List is one CSV row, everywhere: for its shape, for broadcasting and for every row and column position (`INDEX(x, 2, 1)` is `#REF!`, as `CHOOSEROWS(x, 2)` is `#VALUE!`). A Frame column runs down the rows, so read whole in a formula it is a one-column table, as an Excel table column is. A function whose answer is a column in Excel because of what it does keeps that shape as a one-column table: TOCOL, MAKEARRAY with one column, and BYROW. SEQUENCE(n) stays a list.

**Direction is declared per function.** Every function that takes a whole list declares, on its own entry, whether a vector's direction matters to it. A direction-free function reads a one-column or one-row table as its items and answers a list the way its first vector came in, so a column in is a column out. An axis-aware function (SORT, TAKE, VSTACK) gets the table as it is and reads its rows and columns itself.

## Why

[[C15]] matricesInFormulas counts a list as one row, and [[A5]] excelParity wants Excel's answer. A list is one CSV row, so a Frame column read as a list was turned sideways: `ROWS(price)` was 1, and SORT or TAKE worked across it. When a column-shaped answer collapsed into a list it turned into a row too, so the answers that depend on the shape came out wrong without an error: `m / BYROW(m, SUM)` divided each column by the wrong totals, and `HSTACK(m, BYROW(m, SUM))` spilled the totals across one row. Keeping every column a column makes those formulas right, and it leaves a list with one reading, so a position past row 1 is an error rather than a guess. Most list functions have no sense of direction, so they must read a column as happily as a list, and answering in the shape they were given keeps orientation from flipping mid-formula: `price * REVERSE(price)` pairs values instead of spreading into a grid. SEQUENCE(n) is a series of values whose orientation carries no meaning, and the Sequence card answers a list, so it stays one.

## Consequences

- **Frame from Lists is the named transposer** between the two shapes: each list, a row, becomes a column of the Frame. Get Column goes back, a column into a list. Nothing else turns one into the other silently.
- The declaration is `orient` on the function's entry in `EXCEL_IMPL_META` (`free` or `axis`), so any surface that hands a function a column gets the same reading; a test fails when a list-taking function has none. A table of more than one row and column stays a table under `free`, so a function with a grid mode (INTERPOLATE, DIAGONAL) still gets its grid. How it's applied: [[formula-language]] § Whole-list natives.
- In a computed column, `ROWS(price)` is the row count ([[C22]] rowFormulaRefs), and a wired list with one value per row reads as a column beside the table's own, so `SUM(price * weights)` pairs them.
- A Cube column whose cells hold lists is a stack of rows, one per Cube row, padded with blanks to the longest ([[D81]] cubeRowLists).
- TOROW flattens to a list reading row by row, as Excel's does; it is the way to turn a table or a column into a list.
- TAKE and DROP count a list's items as columns: `TAKE(x, , 2)` is its first two items and `TAKE(x, 2)` the whole list. Reading a list's items as rows instead would take its own toggle on the card and an argument in the formula, never an exception in the rule.
- The Table Reshape card's TOCOL op and the By Axis card's BYROW op answer one-column tables, and switching op retypes the output.
- The INDEX card shows one Position socket on a list, since a list has no second axis to pick. One index walks any one-row or one-column table too, as in Excel, so `INDEX(TOCOL(x), 3)` is its third value.
- INDEX takes a list of positions, as Excel's array arguments, on the card and in the formula, so a list has its own way to pick several items and stay a list. CHOOSEROWS and CHOOSECOLS name rows and columns, so they answer tables even on a list (`CHOOSECOLS(x, 1, 3)` is a one-row table), where TAKE and DROP, whose names say nothing about tables, keep a list a list.
- `INDEX(SEQUENCE(5), 3)` is item 3; `INDEX(SEQUENCE(5), 3, 1)` is `#REF!`.
- SORT and UNIQUE work on rows, as Excel's do, so on a list (one row) they change nothing unless `by_col` is TRUE: `SORT(x)` is `x` as it was, and `SORT(x, , , TRUE)` sorts its items. On a Frame column they sort and dedupe its values, as on an Excel table column. The Sort and UNIQUE cards carry the same choice as a Rows / Columns toggle, defaulting to Rows. FILTER and SORTBY read their mask or keys' shape, so a list with a list of the same length keeps or reorders its items. The author, 2026-09-26: "strict excel. if we have to add affordances for user support, we'll do that. hell we could even throw #SYNTAX! on do-nothing function setups if we have to, though that's drastic. we can add toggles to cards AND, crucially, we could just add a LISTSORT or ROWSORT or whatever custom function we want with differing/shortcut behavior."
- **Reopen if:** SEQUENCE's orientation starts to matter to a formula people write, or a function needs direction for one argument and not another (the declaration then moves to the argument).

## Contest

### Contest 2026-09-29 by Claude Opus 5.5: keep wins

Keep wins against C15 and A5: a list is one row is what C15 counts and what keeps Excel's shape-dependent answers right. Opposite (a list is a column) breaks every rank-1 answer the formula surface already gives. Deletion leaves the orientation of TOCOL, BYROW and friends to each function. The node is widened, not reversed, on the author's word: it now states the whole model, a List is one CSV row and a Frame column is a one-column table, absorbing E17.
