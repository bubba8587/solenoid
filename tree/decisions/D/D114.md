## Decision
A date is one of the value kinds, beside number, text and logical, and it is represented the way they are: a value is a date the way a value is text, by what it is, wherever it is. A loose date, an item in a list and a cell in a table are all date values. Nothing outside the value decides that a number is a date: not the socket it arrived on, not the column it sits in, not a rule that guesses from a formula's text.

## Why
[[B17]] typedValueModel already names date as a kind beside number, text and logical, but the code held it as a number with the date-ness kept beside it (in sockets, column types and relayed source types), and every serial that leaked had lost that in transit. Holding a date the way text and logicals are held makes it impossible to drop, and makes the date kind work like the kinds the rule already lists.

## Consequences
- A date stays a date through every card, list, lookup, branch, LAMBDA and export without any card having to know.
- A card's output type after a run is read off the values it carried ([[C136]] typesKnownAfterCalc).
- With date a kind, [[C10]] socketLattice covers its crossings: a number is not read as a date or a date as a number without Cast. [[C137]], [[C44]] dateSerials and [[C118]] formatTravelsWithValue cover how it shows.
- **Reopen if:** holding dates as their own kind costs measurable speed on large tables that a number with a column type would not.
