## Decision

**MUST:** a matrix reaches a function whole only when the function's registration declares `matrixArgs`. Otherwise:

- a range aggregate flattens the matrix row by row before its usual 1-D preparation;
- a positional lookup or a 1-D whole-list native answers `#SHAPE!`;
- an internally registered element-wise function broadcasts over the cells;
- an undeclared Formula.js name refuses the matrix with one clean `#SHAPE!`, never an array of per-cell `#VALUE!`s.

So Formula.js only ever receives lists and scalars, permanently.

**MUST:** a complex number reaches a function only when its registration declares `cxArgs`, which the IM* family does. Anywhere else a complex operand answers a `#TYPE!` that names the IM* family. Three kinds of function are exempt, because they must see their operand as it is: the `NULL_INSPECTING` value-passers (IF hands a complex branch through, and the type checks must see it), the `ERROR_HANDLER_FUNCTIONS` (a catcher sees its raw operand), and the whole-list natives, whose position-preserving ops treat elements as opaque (`REVERSE` of a complex list is legitimate).

## Why

Formula.js's array functions are written against 2-D spreadsheet ranges and have untested quirks, and one has been caught changing its arguments in place (CHISQ.TEST). The old formula rank cap was partly there to contain that, and when [[C15]] matricesInFormulas lifted the cap, the containment had to stay. Before the gate, UNIQUE, SORT, MODE.MULT and FREQUENCY dispatched through Formula.js and broadcast element-wise, so `UNIQUE([3,1,3,2])` answered a column of singletons, and TREND, GROWTH, LINEST and LOGEST returned plausible-looking garbage the same way. Complex numbers had the same problem: before the gate, `cx + 1` produced the text `"[object Object]1"`, and Formula.js's IM* functions accepted complex numbers written as text while refusing the graph's own complex values.
