## Decision

Wherever text becomes a value of a declared type (a Frame Input cell, a List Input item typed or wired, an inline list field on any card, an item in a typed Cube list), it is read one way, the way a Frame Input cell is read. Text the type can't read is NaN, dirty data shown as `NaN`, never a silent blank; a date the type can't settle stays its error. List Input also keeps its typed text beside each value, so the list popup's Source view shows what was typed.

## Why

[[C58]] tableInputRawText makes what was typed the stored truth, and a reading that turns unreadable text into a blank hides that anything was typed at all: a blank is a real missing value that totals skip ([[C24]] arraySemantics). Several readers with different answers for the same text meant the same `abc` was a blank in one place and NaN in the next, so a user could not predict what a cell held. One reader means one rule to learn.

## Consequences

- A date list shows a NaN item as `NaN`, in its value box and popup, as a Frame's date column does ([[format-model]]).
- A bare number typed into a Date list is a day serial, as in a Frame's Date column (2024 is 16-Jul-1905). `yes` and `no` are not Booleans in a list field, as in a Frame cell.
- NaN is a number, so COUNT counts it, the same as in a Frame column.
- List Input's card stays view-only for the popup: it hands the popup only the typed text, never a save callback ([[literal-input-editors]] § List Input is not one of them).
- **Reopen if:** Frame Input's cell reading changes; everything here follows it.
