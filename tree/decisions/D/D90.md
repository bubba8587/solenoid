## Decision

Every level of a Cube types its own columns. A column either declares an element type (Number, Text, Date, Boolean) or declares none, and a declared type holds the column's values and the items of its lists: a value reads as a Frame cell of that type does (what it can't read shows as NaN), a list item as a List Input item does (what it can't read is blank). A table nested in the column never takes that type; its columns carry types of their own, declared the same way, at any depth. A nested column's type holds that column in every row's table. The text as typed is never rewritten.

## Why

[[C10]] socketLattice keeps kinds from mixing on their own, and a Frame column enforces that by having one type. A Cube is the container for data that doesn't flatten, so forcing a type on every column would refuse the vault notes and hand-typed records it exists to hold; letting each column say which it is keeps both. A list in a column is that column's values spread out, so the column's type is its items' type. A nested table is not: its columns hold different things (a task list's names beside its hours), so one type pushed onto all of them makes most of them NaN or blank, and a nested Frame or Cube is only as trustworthy as a top-level one when it types its columns the same way. Tying a nested column's type to the column rather than to one row's table keeps a Cube's rows alike, as a Frame column is alike down its rows. The source stays as typed ([[C58]] tableInputRawText), so a type is a reading, never a rewrite.

## Consequences

- Cube Input's column type button cycles None, Number, Text, Date, Boolean and Formula on the top level; on a nested level it cycles the same types without Formula. A new column starts with none. The Solenoid Properties plugin's cube editor has the same buttons without Formula, and saves the picks as it saves a Frame's.
- A column may carry a type and nested column types at once: the type reads its values and lists, the nested types read its tables.
- A list mixing kinds in an untyped column claims no kind: it always shows its items as they are (its chip in the neutral gray, its popup as text), and a Cast converts it item by item.
- The editor shows each typed cell's reading, and the Source switch shows what was typed.
- An inferred type on a column nobody typed is a display hint only.
- How it's built: the frame-verbs spec (The Cube value) and the table-popup spec (Editing a Cube Input).
- **Reopen if:** one row's nested table needs column types that differ from the same column's tables in other rows.

## Contest

Carried from D80, which this node supersedes.

### Contest 2026-09-28 by Claude (agent): variant wins

- keep: D80 as written types a nested table's every column with the parent column's type. Its own Reopen names this case, and the author asked for it: a Number column holding a task table turns the names column NaN. Fails C10's aim (kinds honest per column) one level down.
- opposite: a declared type holds nothing but top-level scalars; lists keep their own kinds. Loses the list reading the author endorsed ("a typed cube column can override a List in its type").
- deletion: C10 alone doesn't say how a mixed container column reads; a person could choose otherwise, so a leaf is needed.
- variant (chosen): a column's type holds its values and list items; a nested table types its own columns at every depth, keyed by the column, never inherited. Cost: a nested schema in Cube Input's source and the plugin's column-type store, a type button on nested levels. Chosen on the author's word (2026-09-28).

Variant wins.
