## Decision

Every table in a Cube types its own columns. A column either declares an element type (Number, Text, Date, Boolean) or declares none, and a declared type holds the column's values and the items of its lists and Tables: a value reads as a Frame cell of that type does (what it can't read shows as NaN), an item as a List Input item does (what it can't read is blank). A table nested in a cell never takes its column's type; it carries types of its own, declared the same way, and each cell's table has its own, at any depth, since one column's rows may hold tables of entirely different shapes. The text as typed is never rewritten.

## Why

[[C10]] socketLattice keeps kinds from mixing on their own, and a Frame column enforces that by having one type. A Cube is the container for data that doesn't flatten, so forcing a type on every column would refuse the vault notes and hand-typed records it exists to hold; letting each column say which it is keeps both. A list or Table in a column is that column's values spread out, so the column's type is its items' type. A nested table is not: its columns hold different things (a task list's names beside its hours), and in freeform nested data the next row's table may have different columns altogether, so a type pushed down from the column, or shared across rows, types columns that aren't there and misses the ones that are. The source stays as typed ([[C58]] tableInputRawText), so a type is a reading, never a rewrite.

## Consequences

- Cube Input's column type button cycles None, Number, Text, Date, Boolean and Formula on the top level; on a nested table it cycles the same types without Formula, for that one cell's table. A new column starts with none. The Solenoid Properties plugin's cube editor has the same buttons without Formula; it saves the top level's picks as it saves a Frame's (per property, vault-wide) and a nested table's with the note.
- A column may carry a type and have typed tables in its cells at once: the type reads its values, lists and Tables, each nested Frame or Cube reads by its own picks.
- A nested table's picks follow its column when the column is renamed, and go when its column, its row or its cell's contents go.
- A list mixing kinds in an untyped column claims no kind: it always shows its items as they are (its chip in the neutral gray, its popup as text), and a Cast converts it item by item.
- The editor shows each typed cell's reading, and the Source switch shows what was typed.
- An inferred type on a column nobody typed is a display hint only.
- How it's built: the frame-verbs spec (The Cube value) and the table-popup spec (Editing a Cube Input).

Carried from D80, which this node supersedes.

### Contest 2026-09-28 by Claude (agent): variant wins

- keep: D80 as written types a nested table's every column with the parent column's type. Its own Reopen names this case, and the author asked for it: a Number column holding a task table turns the names column NaN. Fails C10's aim (kinds honest per column) one level down.
- opposite: a declared type holds nothing but top-level scalars; lists keep their own kinds. Loses the list reading the author endorsed ("a typed cube column can override a List in its type").
- deletion: C10 alone doesn't say how a mixed container column reads; a person could choose otherwise, so a leaf is needed.
- variant (chosen): a column's type holds its values and list items; a nested table types its own columns at every depth, keyed by the column, never inherited. Cost: a nested schema in Cube Input's source and the plugin's column-type store, a type button on nested levels. Chosen on the author's word (2026-09-28).

Variant wins.
