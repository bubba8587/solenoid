## Decision

Every table in a Cube types its own columns. A column declares a type (Number, Text, Date, Boolean) or none, and a declared type reads the column's values and the items of its lists as a Frame cell of that type reads them. A table nested in a cell never takes its column's type: it declares its own, cell by cell and at any depth, since one column's rows may hold tables of entirely different shapes. What was typed is never rewritten.

## Why

A Cube holds data that doesn't flatten, like vault notes and hand-typed records, so forcing one type on every column would refuse what it exists to hold, while letting each column say which it is keeps kinds honest where they can be ([[C10]] socketLattice). A nested table's columns hold different things (a task list's names beside its hours), and the next row's table may have other columns altogether, so a type pushed down from the column would type columns that aren't there. What was typed stays the stored truth ([[C58]] tableInputRawText), so a type is a reading, never a rewrite.

### Contest 2026-09-28 by Claude (agent): variant wins

- keep: D80 as written types a nested table's every column with the parent column's type. Its own Reopen names this case, and the author asked for it: a Number column holding a task table turns the names column NaN. Fails C10's aim (kinds honest per column) one level down.
- opposite: a declared type holds nothing but top-level scalars; lists keep their own kinds. Loses the list reading the author endorsed ("a typed cube column can override a List in its type").
- deletion: C10 alone doesn't say how a mixed container column reads; a person could choose otherwise, so a leaf is needed.
- variant (chosen): a column's type holds its values and list items; a nested table types its own columns at every depth, keyed by the column, never inherited. Cost: a nested schema in Cube Input's source and the plugin's column-type store, a type button on nested levels. Chosen on the author's word (2026-09-28).

Variant wins.
