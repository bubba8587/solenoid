## Decision

**MUST:** a value's display format (decimals, percent, date style and the like) carries downstream through a step that keeps the value's meaning, and stops at a step that doesn't. It neither stops at every calculation nor rides through all of them. The unit never flows this way: it stays on the value ([[C25]] firstClassUnits), so multiplying $10 keeps the $ and drops the 2-decimal format.

- **Overrides.** A nearer Format Controller overrides what it inherits. Its style dropdown also has a "—" pick that keeps the incoming format and sets only the unit, so a Format Controller added just for a unit doesn't reset the style to Auto.
- **Convert drops the format.** It sets a new unit and rescales the number, so precision chosen for the old unit no longer fits.
- **Looking back stops at a calculation.** A value takes the format of a Format Controller placed after it only when nothing but pass-through nodes sit between them, because a format chosen after a calculation says nothing about the value before it.
- **Frames.** A Frame column's format travels with the column, like its unit, and the nearer node's pick wins.

## Why

[[C25]] firstClassUnits locks a unit to its value. A display format is the opposite, a choice about how to show the value, so it carries down the stream where it can and can always be overridden: the author's call. "Where it can" means a step that keeps the value's meaning. NPV of a 5% rate is not a percent, an integer 7 ÷ 2 is not 4, and date − date is a span, not a date; carrying the first formatted input through every calculation showed exactly those wrong displays.
