## Decision

An input with nothing plugged in uses the value typed on the card. When a blank arrives, what it means depends on what the input is for:

- **Data**, the values a node works on: a blank is a real missing value. It stays blank and passes on ("ok yep data blanks are blank"). A node with no data at all answers blank.
- **A setting**, how the node works on its data (a count, a size, a mode, a digit count): a blank means the setting was left out, so the node uses its default. A blank cable overrides the typed value ("an *overriding* skip- i.e. if I type a position 5 into INDEX, then wire a blank number input cable, that 5 is suppressed until the cable is removed"). A blank item in a list of settings is skipped at its spot the same way.
- **Positions**, which items or rows to pick: a blank pick is dropped. With no picks left, the positions were left out.
- **Nothing to fall back on**: when a setting or the positions have no default, the node says so loudly with `#SYNTAX!` instead of going quiet.

A formula reads its arguments by the same roles, whether a slot is left empty or holds a blank value ("formulas following the same rule: yes"). A left-out size or position keeps the whole thing, where that applies.

The aim, in the author's words: "my intention is to have as few blank results as possible. if we need to make a stink about something missing or blank, we should prioritize using #SYNTAX! to alert the user." And: "in almost no case I can imagine should we need to blank the entire result."

## Why

[[C24]] arraySemantics makes a blank a real value, and for data that protects the answer: a missing price turned into 0 is a believable wrong number. A setting is not data. A blank count is not an unknown count, it is a count nobody gave, and "not given" already means something, the same thing a skipped formula argument means ([[C80]] blankArgIsExcelBlank). Blanking the whole answer there throws away the data that was wired in and protects nothing, and a half-built card that errors tells the user what it still needs ("I think a half-built card erroring is fine? you could always put in default values if need be"). The card already hides the typed value while a cable is plugged in, so the override is visible.

## Consequences

- *Excel diverges:* Excel reads an empty cell in a size slot as 0, so `TAKE(m, A1, 2)` with `A1` empty is `#CALC!` there; here it keeps every row ([[A6]] divergeByDesign). The author: "that's a fine divergence and I think it's a strict upgrade on Excel behavior in this instance".
- *Not yet swept:* only some functions declare their roles so far; the rest keep the older per-role behavior until the sweep reaches them (backlog). Filter's value is among them, and it overturns [[C24]]'s blank-filter consequence when it lands ("I don't really care about C24, it's fine to override and make compliant with other changes").
- The roles, the declaration every function subscribes to, and how each is read: [[input-roles]].
- **Reopen if:** a default would surprise more often than a blank answer would.
