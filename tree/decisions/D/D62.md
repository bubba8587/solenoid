## Decision

The Obsidian and TaskNotes nodes take their source from the first of these that applies:

1. The demo vault, while a marketing page forces it (`forceDemoVault`, `forceDemoTaskNotes`). The page clears the force when it closes and never writes to the user's settings.
2. The vault folder or TaskNotes URL set in Settings.
3. The bundled demo vault, while "Use demo vault" (`useDemoVault`, on by default) is on.
4. Nothing, in which case the nodes ask the user to set the folder.

The demo switch is a fallback, not an override: it can never show the demo beside a configured vault. In Settings the vault folder comes first and the demo switch second, with the help text "Enable the demo vault for usage on the web app and when no other vault is selected."

## Why

The demo vault used to sit behind a setting a new user would never find, so every Obsidian example shipped a frozen copy of its data beside the live node just so it computed somewhere. That doubled the nodes and suggested the live node was optional. Making the demo the default for an unconfigured app means the first open shows real notes and tasks, and on the web, which has no filesystem ([[C1]] demoVault), the demo is the only thing the nodes can show. Setting a real vault replaces the demo the moment it is set. That the demo never overrides a real vault is the author's call.

Marketing pages force the demo separately because a visitor's saved setting must not decide what the page shows ([[C2]] realCanvasScenes), and flipping the setting on their behalf would leak into their real app. One force switch moves the vault root and the Local File data folder together.

## Consequences

- The example documents wire the live Vault Folder or TaskNotes node directly, with no frozen copy of the data beside it.
- **Reopen if:** the web app gets a real filesystem, or a second demo source appears that one switch cannot cover.
