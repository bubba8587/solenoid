## Decision

Solenoid positions itself as the computation layer for an Obsidian vault, rather than a standalone calculator people feed by hand: it reads notes, their frontmatter and TaskNotes data, and writes computed values back. This is its main route to adoption.

Writing a note's body (a filled template, a Report, a direct write) matters as much as writing its properties, and more. Tools for managing Obsidian properties already exist, and Solenoid adds little there; its value is computed content landing in the note itself.

## Why

[[A1]] visualGraphCalculator reaches up to data tables, and a table needs data someone already keeps. An Obsidian vault is that data: notes whose properties and TaskNotes tasks are already tables, with no calculator attached. Meeting people there gives the table end of the product real data from the first minute, where a standalone app makes every newcomer type or import theirs first. The body matters more than the properties because an answer written into the note lands where the person reads it. Choosing Obsidian as the bet is the author's call.

## Alternatives considered

### Contest 2026-09-15 by Claude Opus 5: keep wins

Rubric: [[A1]] (a visual node-graph calculator, scratchpad to tables).
- keep: Obsidian + TaskNotes integration is the flagship adoption bet. Cost: the vault readers, sinks and demo vault already built; ongoing plugin-API tracking.
- opposite: no flagship integration; Solenoid stands alone. Every user brings data by hand, the slow adoption path the bet exists to avoid; [[A1]]'s table end has no data to work on.
- deletion: [[A1]] alone does not say which audience to court first, so integration priority would be re-argued each session.
- variant: a generic folder-of-files integration with no Obsidian specifics. Cheaper, but loses TaskNotes' structured frontmatter, the concrete demo that makes the table end real.
Verdict: keep. The owner named this the adoption breakthrough (2026-09-07).
