## Decision

One node, with a picker for whatever varies. When several nodes could be one, they all become one, never just two of them. A variant of a node is an option on that node, never a separate node beside it.

## Why

[[A1]] wants a calculator that is easy to learn at scratchpad size and still covers table work. Every extra node is another name to find in the Add menu, another thing to learn, and another thing to keep in step with its formula. Running totals ([[C60]] oneRunningNode) and the distributions ([[C61]] oneDistributionNode) are the models. A distribution merge once stopped at two when the intent was all fourteen.

## Consequences

- Where the combinations are few, a flat list of options beats a second picker: each option keeps its own hover description (Hypothesis Test's six tests, Rank & Percentile's INC and EXC forms).
- The Add menu and the Function Reference keep every old entry, and each one now opens the merged node. Old saves that used a retired node load as placeholders ([[B7]] preAlphaBreakFreely).
- How a merge is built is in the node-classes floor spec.
- **Reopen if:** a family whose variants really take different inputs (a second x value, a parameter that isn't a number). Then a separate node is honest, and the reason is recorded.

## Alternatives considered

### Contest 2026-09-15 by Claude Opus 5: keep wins

Rubric: [[A1]].
- keep: maximal merges, variants as selectors. Cost: spec tables per family; socket-swap and prune mechanics on each merged card.
- opposite: one node per variant. The Add menu and Reference grow by every variant; each is another parity target and another name to learn.
- deletion: [[A1]] alone would not stop sibling nodes accreting one session at a time, the observed failure (a pairwise distribution merge).
- variant: merge only when the author asks, pairwise otherwise. The recorded stall at pairwise is exactly this variant's cost.
Verdict: keep.
