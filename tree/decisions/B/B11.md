## Decision

When something varies within a node family, it's an option on one node, never a separate node beside it. When several nodes could be one, they all become one, never just two of them.

## Why

Solenoid has to stay easy to learn even as it covers more, and every extra node is another name to find in the Add menu and another thing to learn. A merge that stops partway leaves that cost behind, so a merge goes all the way.

## Consequences

- Old Add menu and Function Reference entries keep working and open the merged node.
- How a merge is built: [[node-classes]].
- **Reopen if:** a family's variants really take different inputs (a second x value, a parameter that isn't a number). Then a separate node is honest, and the reason is recorded.

## Alternatives considered

### Contest 2026-09-15 by Claude Opus 5: keep wins

Rubric: [[A1]].
- keep: maximal merges, variants as selectors. Cost: spec tables per family; socket-swap and prune mechanics on each merged card.
- opposite: one node per variant. The Add menu and Reference grow by every variant; each is another parity target and another name to learn.
- deletion: [[A1]] alone would not stop sibling nodes accreting one session at a time, the observed failure (a pairwise distribution merge).
- variant: merge only when the author asks, pairwise otherwise. The recorded stall at pairwise is exactly this variant's cost.
Verdict: keep.
