## Decision

Whatever a save captures, a load restores and the next save re-captures identically, and every save path fails loudly rather than writing a valid-looking file that has lost something. The document's text form is the canonical projection every save derives from.

## Why

[[A1]]'s calculator is only usable if the work survives. Every save-path failure found to date wrote a valid-looking file and surfaced only on reload, the worst kind of loss because nothing marks it when it happens.

## Consequences

Parent of the save-path rules: [[C29]] plainJsonInit, [[C30]] saveViaTextForm, [[C31]] immutableDocStore, [[C32]] autosaveSlotOrder, [[C33]] saveBindsMain, [[C34]] classNameIsType, [[C35]] unknownViaPlaceholder, [[C36]] captureBeforeSwap, [[D50]] everyFieldClassified, [[C37]] observerOwnsSize.

## Alternatives considered

### Contest 2026-09-15 by Claude Opus 5: keep wins

Rubric: [[A1]].
- keep: saves are lossless and loud. Cost: the persistence fixed-point and field-classification sweeps, slot rotation, text-form completeness scan.
- opposite: best-effort saves; occasional loss accepted for speed of change. A calculator that loses a setting on reload is not usable for real work.
- deletion: [[A1]] alone does not name persistence; the save-path rules would hang on the engine or the view, neither of which is why they exist.
- variant: lossless only for values, settings may reset. The recorded bug (an as-of join direction resetting on reload) is this variant's cost.
Verdict: keep.
