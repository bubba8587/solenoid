## Decision

The canvas is drawn by React Flow, not by rete's own renderer. Underneath it, the graph and the engine that computes it stay on the small rete core libraries, rather than code of our own.

## Why

[[A1]] visualGraphCalculator needs a canvas that draws smoothly and a graph that computes typed values, and no one library does both. React Flow for the canvas is the author's call; it only draws, and has no idea of typed sockets or of values flowing through a graph. The rete core that supplies those is small, does the job, and no other library fits better. Writing our own would replace code someone else maintains with code we maintain, for no gain the user would see. What the app uses from rete is listed in the React Flow surface spec.

## Consequences

- The canvas has one way of being drawn. A second or third renderer is not built ([[C42]] htmlInCanvasRenderer).
- **Reopen if:** rete core stops being maintained in a way that hurts (a React or TypeScript upgrade it can't follow), or a library appears that would let us delete code rather than rename it.

## Alternatives considered

### Contest 2026-09-15 by Claude Opus 5: keep wins

Rubric: [[A1]].
- keep: React Flow view, rete core + rete-engine headless. Cost: already landed; ~1,500 vendored lines to track.
- opposite: rete renders again. The port was done because the rete render stack could not carry the canvas the author wanted; re-porting back is the whole port's cost again.
- deletion: [[A1]] says visual node graph but not what draws or computes it; every canvas change would re-open the stack.
- variant: hand-rolled model and engine under React Flow. ~400 lines of ours for no functional gain, a new engine to trust.
Verdict: keep.
