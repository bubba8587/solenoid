## Decision

Desktop is the full product, with a fast native table engine and real file access; the web build is for looking and trying. A feature that needs files degrades to a no-filesystem path on the web instead of being a dead end there.

A desktop-only feature is built without hesitation. "It won't work on the web" is never an objection, because the web build is look-and-try by design.

## Why

This decision exists because agents would otherwise object to features which work on desktop but not web. It also establishes the adoption strategy. Solenoid is small and loads quite fast, and the desktop version is a Tauri shell, so there's no visual degradation between the two. A casual user likely never even needs the desktop app, a serious user can get the desktop app.
## Alternatives considered

Full web build: Needs a production Polars-WASM or DuckDB path and a real filesystem story; reopens the relational-engine choice.
