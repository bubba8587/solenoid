# Spec: Rust 1.100 on the bleeding-edge branch

Serves [[B26]] edgeReadsReleaseNotes and [[B25]] edgeReadyToPort. Rust 1.100.0 came out on 2026-11-12 ([announcement](https://blog.rust-lang.org/2026/11/12/Rust-1.100.0/)). This is everything it offered, read against the crates: what the branch uses and what it replaced, what was read and has no place here, what was measured and left alone, and what is still open. It is written for the agent who takes this to a work branch ([[#Taking it to a work branch]]); the pin there moved to 1.100.0 the same day. The one-line rows are in [[platform-features#Toolchain and dependency features in use]].

## State on 2026-11-12

The branch sits on `develop` @ `15cf43ad0` with stable 1.100.0 (`rust-toolchain.toml` says `stable` here; `develop` pins `1.100.0` since `07a8a3b9b`). Before any change, fmt and clippy passed on all four crates under 1.100, natively and for wasm: the new toolchain broke nothing. After the changes below, fmt, clippy and `cargo test --release` pass on `solenoid-schedule`, `solenoid-core` and `solenoid-graph`, and fmt and clippy on `solenoid-parquet`; through the rebuilt engine module, the typecheck and the whole TypeScript suite pass too. `src-tauri` was not built (its `rust-version` moved with the others, nothing else in it changed).

## In use

Each is one commit. None moves an answer: every new call is defined in the standard library as the expression it replaced.

| Feature | Commit | Where | What it replaced |
|---|---|---|---|
| `rust-version = "1.100"` | `Edge: Rust 1.100 as every crate's rust-version` | The four crates and `src-tauri` | `1.99` |
| The never type `!` in a type position | `Edge: the never type: …` | `nodes/kit.rs`, `eval.rs`: the two `date_values::call`s whose body can't fail | `Ok::<_, std::convert::Infallible>` |
| `bool::toggle` | `Edge: bool::toggle: …` | Four flags: `fns_stats.rs`, `excel_formula.rs`, `frame_verbs.rs`, the graph's `text_form.rs` | `x = !x` |
| `Box::map` | `Edge: Box::map: …` | `excel_formula.rs`: `bind_bracket_params` and `bracket_params`, ten boxes | `Box::new(f(*child))`, a free and an allocation per rewritten node; `Box::map` writes the result back into the same box |
| `std::mem::DropGuard` | `Edge: DropGuard: …` | `eval.rs`: the call-depth counter (`CallDepth::enter`), ROW()'s row over a computed column, a LAMBDA body's snapping root (`call_lambda`); `unit_dims.rs`: the scoped LAMBDAs of `dim_eval_with_code` | Two structs with a `Drop` impl each, and two restores written as a statement after the call. The restore now also runs when the call unwinds |
| `Vec::from_fn` | `Edge: Vec::from_fn: …` | 210 sites in 53 files, tests and the bench included | `(0..n).map(f).collect()` |
| `str::trim_prefix`, `str::trim_suffix`, and the same on slices | `Edge: str::trim_prefix and trim_suffix: …` | 28 sites in 17 files of the core and the schedule crate | `s.strip_prefix(p).unwrap_or(s)` |

**Left as they were, on purpose.**
- `Calc` (`excel_functions.rs`) keeps its own type and `Drop` impl: it carries a flag, is `#[must_use]`, and is named in three modules. A `DropGuard` there would hide the name.
- Five `(0..n).map(f).collect()` sites the compiler refuses as `Vec::from_fn`: a `u32` or `i32` index (`excel_functions.rs` `SPAN`, `nodes/probability.rs`, `nodes/visual.rs`), and two whose length draws from the same random source the cell does (`excel_functions.rs`, `tests/properties.rs`).
- Two prefix reads that try a second prefix with `or_else` (`excel_criteria.rs`), and `tests/csv.rs`, whose fallback is `""`, not the text.

## The sweep, run again

`.github/bleeding-edge/rust-1.100-sweep.py` redoes the five mechanical rewrites (everything above but `DropGuard` and the `rust-version`) on any tree: it rewrites, compiles every crate natively and for wasm, puts back each `Vec::from_fn` site the compiler refuses, and formats. `--dry-run` only counts. Run on the commit before the sweeps, it finds 215 `Vec::from_fn` sites and puts five back, and 28 trim, 4 toggle, 10 `Box::map` and 2 never-type sites.

Use it instead of the commits whenever they stop applying. The `Vec::from_fn` commit touches 53 files, so new work on a base will conflict with it, and the generator drops a carried commit that conflicts outside the dependency files ([[branch#The generator]]). When the report names it as dropped, run the script on the rebased branch and commit the result under the same subject. That happened the day it was written: the rebase onto `037066f9c` dropped the commit over `xlsx.rs`, and the script put it back.

`DropGuard` is by hand. The four sites are listed above; the pattern at each is `let outer = X.replace(new); let _guard = DropGuard::new(outer, |outer| X.set(outer));` followed by the call as the tail expression, or `DropGuard::new((), |()| …)` where nothing is held.

## Read, with nothing to use

- **The never-type fallback** changing from `()` to `!` on the 2015 to 2021 editions: every crate is on 2024, where it already was.
- **Conjuring a zero-sized value (`std::mem`), and the unsafe cell's `replace` and two unchecked reference reads**: the four crates forbid `unsafe` (`#![forbid(unsafe_code)]`), and the shell's three `unsafe` blocks are FFI calls with no zero-sized token or cell.
- **`Rc::map`, `Arc::map`, `Box::take`**: no site maps an `Rc` it owns into a value of the same size; the `Rc::new(from_core(&r))` calls build from a borrowed frame of another type.
- **`impl Default for Once`, `PartialEq<Cow<[U]>>` for `Vec` and slices, `AsRef`/`AsMut` for `!`**: no `Once`, and no `Cow` of a slice compared with a list.
- **`Path::trim_prefix`, `Child::main_thread_handle`, `CommandExt::show_window`**: the shell strips no path prefix and starts no process.
- **Cargo's build-directory layout** (the configuration hash moves from file names to the parent directory): nothing reads intermediate files. `scripts/build-wasm.mjs` and the desktop workflow read final artifacts only (`target/wasm32-unknown-unknown/<profile>/<lib>.wasm`, `src-tauri/target/release/…`), which keep their place.

## The Allocator API: measured, not used

`std::alloc::Allocator` is stable with `Vec` and `Box` only. Solenoid has no allocator of its own for it to replace, so the question was whether a per-call arena would pay. The count, from `crates/solenoid-core/tests/alloc_probe.rs` (a global allocator that counts, the slope between 20,000 and 40,000 rows):

| Formula | Allocations per row | Bytes per row |
|---|---|---|
| `ROUND(l * 1.07 + 3, 2)` | 3.1 | 127 |
| `UPPER(t)` | 2.0 | 66 |
| `MAP(l, LAMBDA(x, LET(y, x * 2, y + 1)))` | 7.0 | 409 |
| `SCAN(0, l, LAMBDA(a, x, a + x))` | 7.0 | 696 |
| `MAP(l, LAMBDA(x, ROUND(x * 1.07 + 3, 2)))` | 10.1 | 416 |
| `MAP(l, LAMBDA(x, IF(x > 0, MAX(x, 1), MIN(x, -1))))` | 14.0 | 735 |
| `MAP(t, LAMBDA(x, UPPER(LEFT(x, 3))))` | 18.0 | 552 |

`SUM(l)`, `IF(l > 0, l, 0)` and `BYROW(l, LAMBDA(r, SUM(r)))` add none per row.

So a LAMBDA called once per row is where the allocations are: 7 to 18 each. An arena is still the wrong first tool, for three reasons.
- **It reaches only part of them.** A call's cost is its argument list (`Vec<V>`), the LAMBDA's environment (`FxHashMap`, in `Eval::lambda_body`), and the values themselves (`Rc` lists, strings). Only the `Vec` can take an allocator in 1.100; maps, `Rc` and `String` can't yet.
- **It needs `unsafe`.** `Allocator` is an `unsafe trait`, and all four crates forbid `unsafe`. An arena would live in a fifth crate that allows it, the first hand-written `unsafe` in the engine.
- **The type spreads.** `Vec<V, A>` is a different type from `Vec<V>`, so `date_values::call`, `Eval::call_with` and every function body that takes its arguments by value would grow a parameter.

What this found instead is plain work that needs no new feature and is not done: a LAMBDA call that allocates less (the environment as a small list of pairs, or one reused across the rows; the argument list reused). It is a speedup with no change of answer, so it is free to take on a work branch; measure it with the probe before and after, and time it on the path the app runs (`tests/graph/passBench.test.ts`).

**What would reopen the arena:** the Allocators project stabilizing `HashMap`, `Rc` and `String` with an allocator, and the probe still showing the calls as the cost after the plain fix.

## Cargo 1.100

- **Unused dependencies are reported** (`cargo::unused_dependencies`, warn by default, read from `[lints.cargo]`). One report, and it is true: `wasm-bindgen-futures` in `crates/solenoid-graph`, when the crate is built for wasm with `--features plugin`. The modules that use it (`boundary`, `wasm`) are compiled out of the Obsidian plugin's module, so that build compiles a crate it never calls. It is a warning from Cargo, not from rustc, so `-D warnings` doesn't fail on it, and `-q` in `scripts/check-rust.sh` doesn't hide it. **Open**, see below.
- **`min-publish-age`** (`[registry] global-min-publish-age` in `.cargo/config.toml`: Cargo skips a version published more recently when it resolves a lockfile, and refuses a requirement only such a version meets). On for the work branches at 7 days, at the author's word (`develop` @ `15cf43ad0`). Off here ([[branch#Dependencies]]). Cargo 1.99 ignored the setting with a warning, so the pin moved with it. `cargo install` ignores it.

## Open

1. **The plugin build's unused `wasm-bindgen-futures`.** Cargo can't say "not when a feature is on", and a `target.'cfg(…)'` table doesn't read features. The fix that makes the report go away is an additive feature: `engine = ["dep:wasm-bindgen-futures"]`, on by default, the seven `not(feature = "plugin")` gates in `crates/solenoid-graph/src` reading `feature = "engine"`, and the plugin's builds passing `--no-default-features --features plugin` (`scripts/build-wasm.mjs`, `scripts/check-rust.sh`, `engine-test.yml`, and the generator's wasm clippy). It trades the warning for a way to build both at once by forgetting `--no-default-features`, so add a `compile_error!` for `engine` with `plugin`. Not done: it changes how CI builds the plugin, and the warning costs build time only.
2. **The LAMBDA call's allocations** ([[#The Allocator API: measured, not used]]).
3. **A check that fails on Cargo's lints.** `cargo check` exits 0 with a Cargo warning. If an unused dependency should fail CI, `[lints.cargo] unused_dependencies = "deny"` in each manifest does it, after item 1.
4. **Not run on this pass:** `src-tauri`'s `cargo check` (it needs WebKitGTK's development libraries; the daily run has them), and the generator's full report. The next daily run writes the report and lists the toolchain as moved.

## Taking it to a work branch

The one thing that held these back is gone: `develop` builds with Rust 1.100.0 since 2026-11-12, and its unchanged crates passed fmt, clippy, the release tests and the TypeScript suite on it. No engine, look or answer is involved. They are not port-checked onto that base yet ([[branch#Porting a finding]]); the daily report does it, and a finding is ready when its check passes there ([[B25]] edgeReadyToPort).

On the work branch:

1. Run `bash scripts/check-rust.sh`, to start from a clean verdict.
2. Port `Edge: Rust 1.100 as every crate's rust-version` first, then the never type, `bool::toggle`, `Box::map`, `DropGuard` and the trim commit with `node .github/bleeding-edge/port.mjs <commit>`.
3. For `Vec::from_fn`, try the port; if it conflicts, run the sweep script on the work branch instead and commit what it leaves. The script needs no commit from this branch.
4. Then `npm run build:wasm` once, the TypeScript tests through it, and `cargo test --release` on the core and the graph, as for any Rust change.
5. Decide the two open items above.
