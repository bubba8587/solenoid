## Decision

- `ElementImage` is only `{width, height, close()}`, NOT an ImageBitmapSource (by spec, permanently): neither `createImageBitmap(refImg)` nor a scratch-canvas bitmap path works on shipping builds, so the mip pyramid builds via in-paint raster + region snapshot.
- A snapshot of the canvas children is recorded just before the `paint` event, so `drawElementImage` OUTSIDE the paint handler draws the PREVIOUS snapshot: every frame that must call it routes through `requestPaint`, and the paint handler re-reads the freshest camera.
- `drawElementImage` returns (and `getElementTransform` computes) the CSS matrix that places the element exactly where it was drawn, which reports the PRESENTED camera for domSync. The spec home for `getElementTransform` is the 2D context, but some builds hang it off the canvas: probe both.

## Why

Verified 2026-07 (Chromium origin trial 148–150, Android DevTrial since 138; behind `chrome://flags/#canvas-draw-element`). The paint can land a frame after the rAF that scheduled it; drawing outside the paint handler is the "canvas a frame behind the DOM" bug at its source.
