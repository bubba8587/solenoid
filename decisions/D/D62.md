## Decision

A configured `obsidianVault` or `taskNotesUrl` always wins. When one is blank, the reader falls back to the bundled demo (the demo vault root, the canned TaskNotes replies) while the `useDemoVault` setting allows it; the setting is on by default and is the web app's only path. With it off and nothing configured, the readers say to set the folder. The setting never overrides a real setup; only the marketing pages' `force*` switches do. An Obsidian seed therefore carries no snapshot input beside its live reader.

Ruled by the author 2026-09-16: the vault folder is the first setting in the Obsidian group, the demo switch second, and the switch is a fallback ("Enable the demo vault for usage on the web app and when no other vault is selected"), not an override beside a real vault.

## Why

B2 says the web is look-and-try and readers must work with no filesystem; C1 gave them a demo vault behind a setting nobody new has found. Every Obsidian seed shipped a snapshot Frame/Cube Input next to its live node so it would compute somewhere, which doubled the nodes and told the reader the live one was optional. With the demo as the unconfigured default, the seeds wire the live node only, the first open of the app shows real notes and tasks, and configuring a vault or a URL replaces the demo the moment it is set.

## Consequences

*Enforced by:* `demoVault.test.ts` → "a configured folder always wins; the demo is the fallback only while the setting allows it (dte:D62 noSetupMeansDemo)"; `obsidian.test.ts` → "armed but off-desktop → the desktop-only guard; with no vault set, the demo's read-only guard (dte:D62 noSetupMeansDemo)".
*Where:* `getVaultRoot()` in `demoVault.ts`, `isDemoTaskNotes()` in `demoTaskNotes.ts`, the Obsidian group in `settingsStore.ts` (`useDemoVault` defaults on).
*Reopen if:* the web app gains a real filesystem, or a second demo source appears that the one switch can't cover.
