## Decision

The Obsidian nodes need a vault to read. Here is how they pick one.

If you have set a vault folder in Settings, that is the vault. Same for the TaskNotes URL. A real setup always wins.

If you have not set one, the nodes use the demo vault that ships with the app, as long as "Use demo vault" is on. It is on by default, and it is the only way the web app can show anything, because the web app has no filesystem. Turn it off with no vault set and the nodes tell you to set the folder.

The marketing pages are the one exception. They force the demo vault while they are on screen, whatever your settings say, and put things back when they close. They never write to your settings.

So the order is: forced by a marketing page, else your configured vault, else the demo if allowed, else nothing.

Because of this, the example documents wire the live Vault Folder or TaskNotes node directly. They no longer need a frozen copy of the data sitting beside it.

The author ruled on 2026-09-16 that the demo switch is a fallback, not an override: you cannot turn on the demo beside a real vault. In Settings the vault folder comes first and the demo switch second, with the help text "Enable the demo vault for usage on the web app and when no other vault is selected."

## Why

The demo vault existed before this, but only behind a setting nobody new would find. So every Obsidian example shipped a frozen copy of its data next to the live node, just so the example computed somewhere. That doubled the nodes and told the reader the live node was optional. Making the demo the default for an unconfigured app fixes that: the first open shows real notes and tasks, and setting a vault replaces the demo the moment you do.

The marketing pages force the demo separately because a visitor's saved setting must not decide what the page shows, and flipping the setting for them would leak into their real app. One force switch moves the vault root and the Local File data folder together.

## Consequences

Tests: `demoVault.test.ts` ("the force wins over the settings and pins both root and data folder"; "a configured folder always wins; the demo is the fallback only while the setting allows it ([[[D62]]] demoVaultResolution)") and `obsidian.test.ts` ("armed but off-desktop → the desktop-only guard; with no vault set, the demo's read-only guard ([[[D62]]] demoVaultResolution)").

Code: `getVaultRoot()` and `forceDemoVault()` in `demoVault.ts`; `isDemoTaskNotes()` and `forceDemoTaskNotes()` in `demoTaskNotes.ts`; the force call in `ObsidianPage.tsx`; the Obsidian group in `settingsStore.ts`, where `useDemoVault` defaults on.

Reopen if the web app ever gets a real filesystem, or a second demo source shows up that one switch cannot cover.
