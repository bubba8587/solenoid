## Decision

The app ships a read-only demo vault (`demoVault.ts`, `demoVaultData.ts`) behind the sentinel root `solenoid:demo-vault`. The path-aware `fs()` dispatch in `fileBridge` sends any path under that root to an in-memory provider, so the vault readers work with no real filesystem, and every write throws. The demo files are lazy-loaded, so they never weigh down the main bundle.

The same seam serves Local File's data folder: off desktop, `getCsvFolder` may resolve to a demo folder, so Local File can read a bundled CSV on the web. Parquet still needs the native engine.

## Why

[[B1]] needs the vault integration to be demoable, and [[B2]] needs the demo to work on the web, where there is no filesystem. Routing by path leaves desktop file operations on the real filesystem untouched. Extending the seam to Local File lets the Excel-over-CSV marketing scene read a real bundled `expenses.csv` instead of a mockup.

## Consequences

- Which vault a node reads (a configured one, the demo, or the one a marketing page forces) is [[D62]] demoVaultResolution.
