## Decision

Desktop runs native Polars; web runs the JS oracle only, behind the `FrameBackend` seam.

## Why

B2: web is look-and-try and desktop the full product, so the full engine lives on desktop where native Polars runs, and web needs only an identical-answer oracle.

## Consequences

- **Where:** the `FrameBackend` seam; cargo parity tests.
- **Reopen if:** a production Polars-WASM path appears, or web becomes a real target. DuckDB (one engine, two targets) is the scoped alternative; the seam makes the swap one module. Never add a second engine "for web" without reopening this explicitly.
- Standing risks: Polars API churn (pinned 0.46), mitigated by the seam, the JS oracle as reference and cargo parity tests; the web/desktop parity tax is permanent, budget for it.
