## Decision

Desktop runs the full product (native Polars, real file IO); the web build is a look-and-try demo. Features that need files must degrade to a no-filesystem path on web rather than being desktop-only dead ends.

A feature that only works on desktop is built without hesitation. "It will not work on the web" is never an objection to building it; the web build is look-and-try by design.

## Why

Relational work runs on native Polars on desktop and an identical JS oracle on web behind the FrameBackend seam (decisions.md polarsEngine). The web demo has to actually demonstrate the product, so file-backed features need a web story.

## Alternatives considered

### Contest 2026-09-15 by Claude Opus 5: keep wins

Rubric: [[A1]].
- keep: web is look-and-try, desktop the full product; readers work with no real filesystem. Cost: a demo-vault seam and the JS oracle beside Polars.
- opposite: web is the full product. Needs a production Polars-WASM or DuckDB path and a real filesystem story; reopens the relational-engine choice.
- deletion: [[A1]] does not say which target carries the full engine, so every reader and sink would re-ask.
- variant: desktop only, no web build. Loses the instant-loading web app the marketing pages demonstrate on.
Verdict: keep.
